### 1.2 ctx-mod：零摘要换窗

思路是换窗口时不调用模型写摘要，由代码从账本、历史和磁盘文件拼出交接。

- **任务账本**（`ledger_append` / `ledger_read`）：模型每完成一个阶段记一条，包括 task_id、状态、一句话要点、next_step，以及 anchors（文件加一段能唯一定位的原文）。校验规则：
  - 标 `done` 必须在 `evidence` 里给出工具结果的历史编号，并且编号要真实存在；
  - `in_progress` 必须有 next_step，省略时沿用该任务上一条；
  - `request_ref` 把记录挂到对应的用户请求上，协调者派来的任务单独列出；
  - 子代理调用一律拒绝。引擎允许子代理调用 mod 工具，调用会带 `agentId`。
- **完整历史**（`history`）：用户消息、助手回复、工具结果都按递增编号写进 `history-wNNN.jsonl`，每个窗口一个分片。工具结果末尾追加 `[#123]`，这样模型以后可以按编号读原文，不必重跑命令。超长正文和参数另存为 `big-*.txt`，搜索也会扫它们。`search` 默认只搜最近 3 个窗口，没有命中再逐窗往前找，结果里写明搜过哪些窗口。默认跳过引擎塞进来的背景行（附件、钩子上下文），用 `door` 参数可以指定搜这些行。
- **交接生成**（`handoff.ts`）：新窗口的第一条消息包含以下内容，篇幅大约 1–5K token：
  - 最近的用户请求原文。很短的请求会带上它回复的那条助手消息；
  - 用户已定决策：跨全部窗口原文照搬，可以用 `decision_revoke` 撤销；
  - 进行中任务的最近 3 条记录和下一步；
  - 待改位置：按 anchor 从**磁盘现读**的带行号片段；
  - 文件工作集、最近的动作（ctx-mod 自己的工具调用不计入）、子代理名单（含缓存冷热）。
  实测数据：266K→5K、45K→589 token，耗时 7–51 ms，不调用模型。
- **换窗触发**：
  - **用量阈值**：按 40 万窗口算，25 万 / 30 万 / 35 万三级提醒，到任务边界时换。用的是绝对 token 数，不按百分比。提醒**在回合内**通过 `$.session.append` 注入，当前这次请求就能看到（T8）；
  - **模型主动申请**（`context new`）：门槛是距上次换窗至少 30 次真实模型请求、每小时最多 4 次、账本够新（最近一次用户请求之后本窗口记过账，之后的工具结果不超过 5 个）；
  - **接管引擎自动压缩**：自动压缩触发时由 mod 的 `session.compact` 钩子用交接替代摘要。账本不新，或者有超过 25 个工具结果没记账时，交还给引擎自己做摘要；
  - **冷缓存**：缓存已过期且上下文超过 10 万时，先扣下用户消息（写入 `held.json`），换完窗口再提交。反正要整段重写缓存，不如顺手换窗；
  - **加载会重建缓存的工具组之前**（例如 computer-use 会让整段消息缓存重建）：上下文超过 12 万就先换窗。
  - 实现方式：mod 调 `$.command.run({command:'compact'})`，由自己的 compact 钩子返回交接，再用 `$.prompt.submit` 续跑。所有触发路径共用这一个钩子。
- **门槛与回退**：写盘失败、账本不新、刚换过窗口时，不做零摘要换窗，并把原因告诉模型。5 小时额度用到 90% 以上时，换窗后不自动续跑。

### 1.3 ptc-run：程序化工具调用

- 注册一个工具 `run_code`：模型写一段 async JS，在 Node 子进程沙箱里同步调用 `tools.read/write/edit/glob/grep/replace/batch/bash/parallel/test`，只有 `console.log` 的输出和返回值回到上下文。mod 运行时没有 fs，所以 runner 以字符串形式内嵌，由 broker 起子进程执行。
- **过期检查**：
  - 同一程序里先 read 再 edit，会比对 mtime；
  - 跨调用时，用 `tools.revision(path)`（内容 sha256 的前 16 位）配合 `expectedRevision`，内容不一致就整次不写，报 `STALE`；
  - 带 revision 的写操作在 `cc-ptc-locks/` 下加跨进程锁：等锁约 2 秒拿不到就报 `LOCKED`，超过 30 秒的锁视为崩溃遗留，可以接管；
  - `all:true` 可以配 `expect` 声明预期处数，处数不符报 `COUNT_MISMATCH`，什么都不写；
  - 多文件写入不是事务，中途崩溃不会回滚。
- **后台任务**：`bash` 前台超时后不杀进程，转成后台 job，返回 jobId，用 `tools.job({id,wait})` 取结果。也可以直接 `background:true`。job 跨 run_code 调用存活，上限 2 小时。`parallel` 最多 64 条命令、并发不超过 16，结束时清理子进程。
- **输出控制**：超过 `maxChars`（默认 8000）时保留前 70% 和后 30%，中段落盘成 ref（`cc-ptc/`，保留 24 小时），用 `ref.text/page` 按需翻页。
- 错误一律带 `[CODE]` 前缀和 `nextAction`，方便模型自己恢复。
- **模式**：
  - `PTC_RUN_READONLY=1`：只读，只能读工作目录和 `PTC_RUN_RO_ROOTS` 指定的目录；
  - `PTC_DENY_CREDENTIALS=1`：读取类操作拒绝凭据文件；
  - DSH 方言（delegate 的 ptc-only）：多出 `tools.test`，`PTC_RUN_DSH_READ_LIMIT` 可以截断不带 limit 的读取。

## 2. 关键设计决策与原因

1. **交接由代码拼，不让模型写摘要。** 模型摘要贵（要一次完整请求）、慢，还会漏掉“正在做哪一步”。代码拼的交接确定、可测，原文来自历史和磁盘。代价是模型没记账的中间结论会丢，所以设了“账本不新就不准零摘要换窗”这道门。
2. **片段从磁盘现读，不用历史里的旧内容。** 引擎压缩后不会自动补回读过的文件（T4）。交接里的带行号片段是当时的最新内容，新窗口可以直接 Edit，不用先 Read（实测改对了）。
3. **自动压缩发生在回合中间。** 所以交接必须自带“当前请求原文、正在做的步骤、下一步”。早期探针里，模型读到一半被压缩，之后就丢下了任务。这一点和 DSH 的痛点直接相关，见第 3 节。
4. **阈值用绝对 token，而且放得晚。** 每次换窗都会丢细节，也要重写缓存，所以尽量把一个窗口用满。窗口很大时百分比失真：`context.percent` 按模型窗口算，Haiku 是 100 万。
5. **按真实模型请求数计频率，不按工具调用。** 一次请求可能并发好几个工具调用，按工具调用计会误判。
6. **缓存冷了就顺手换窗。** 缓存过期后下一次请求反正要全价重写前缀，这时换成几 K 的交接最划算。
7. **“用户已定决策”单列，原文照搬，可以撤销。** 用户的规则和答复最怕被摘要改写；用户也会反悔，所以加了 `decision_revoke`。
8. **history 默认只搜最近 3 个窗口。** 控制输出量；没命中再自动往前找，并写明搜了哪些窗口，避免模型误以为“历史里没有”。
9. **ptc 的写操作必须可校验。** 模型批量改文件时最常见的事故是基于旧内容改，或者改的处数和预期不符，所以 STALE / COUNT_MISMATCH 都设计成“整次不写”，不做部分写入。
10. **ptc 工具首轮直接可用**（`isDeferred:false`）。延迟加载要多一轮 ToolSearch，而且用户的“始终加载”设置对它不生效。

### 试过但放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| mod 直接调 `$.session.compact()` | 自己的 compact 钩子不跑，无头会话里也直接被拒；改为 `$.command.run('compact')` |
| 在 `prompt.submit` 钩子里直接压缩 | 引擎不允许；改为 drop 这条提示 → 定时器里压缩 → 重新提交（held 机制） |
| 给 ToolSearch 结果追加 `[#编号]` | tool_reference 块被改后 API 返回 400；只给纯文本结果加编号 |
| RED-01：大工具输出先交给小模型压成回执 | Top 30 会话里大输出总共只有 1.82M 字符，即使压缩免费，毛收益也太小 |
| PTC-07：grep 结果分页加快照指纹 | 工作区没改时重跑 grep 只占 Claude 侧 0.07%、DS 请求 0.67% |
| PTC-05 / PTC-10：测试只打印失败摘要；read 默认截断加 more 字段 | 没过 A/B 闸门（DS flash，n=10）。模型只打印 lines、看不到 more，误以为已经读完，又多读几次，费用反而 +9% |
| fork 子代理承接大读取（结果不进主会话） | 前缀确实能命中缓存，但每一步都带着主会话的全部上下文，而且固定继承主模型；比精简子代理和 DS 都贵，收益上限只有 9–15% |
| 重复读取去重 / 缓存未命中治理 | 审计结果：重复读取约占额度 1%，缓存未命中约 5.6%，不值得再做插件 |

## 3. 已知问题，以及可以移植到 DSH 的思路

### 3.1 ctx-mod 已知问题

- 助手在回合中、工具调用之前说的话，有一部分在引擎里是思考块，不进历史。
- 交接后，模型偶尔仍会先“重新摸底”。早期版本换窗后前 7 个请求都在重新探测；加入命令摘要、子代理名单和“先查 history”的引导后，降到 0–1 步。
- 引擎事件的语义随版本变化：例如回合中途消息走的是 delivery 入口，用户消息在无头会话里的来源是 sdk。每次引擎升级都要复核。
- 写放大：首个数据点是逻辑写入 30.7KB、物理写入 213KB，WAF=6.93。分片越大越明显。
- 桌面应用和交互式终端下的部分路径只在假引擎或单元测试里验证过。

### 3.2 针对 DSH 痛点（长回合 187 步不结束、上下文涨到 35 万）

ctx-mod 最关键的一条经验：**换窗/折叠不能只挂在“回合结束”或“空闲”上，必须能在回合中间触发。** 我们最终的设计是：

1. **按请求触发，不按回合。** 每次模型请求前（或每个工具结果返回后）检查上下文 token，过阈值就在**下一次请求之前**做替换。Claude Code 的自动压缩本身就发生在回合中间，ctx-mod 是接管了这个点。DSH 如果有 “before model request” 或 “after tool result” 的 hook，就挂在那里。
2. **分级处理：先提醒，再强制。**
   - 一级：在回合内注入一条提醒，“到任务边界就记账并申请换窗”。模型当次请求就能看到；
   - 二级：要求边做边记账；
   - 三级：不再等模型配合，直接强制替换。账本够新就用零摘要交接，不够新就退回模型摘要。
   这样即使模型一直不结束回合，也一定会在 35 万之前被处理掉。
3. **交接自带“当前回合状态”。** 回合中间折叠后，模型要能接着做同一个回合：当前请求原文、正在做的步骤、下一步、待改文件的最新片段。缺了这些，模型会停下或重做。
4. **用账本和历史编号代替摘要。** 让根代理在长回合里边做边写结构化记录（`done` 必须带证据编号），交接用代码拼，原文留在磁盘可按编号检索。这样折叠不需要额外的模型请求，也不会被摘要改写。
5. **折叠前的门槛。** 检查账本是否够新、未记账的工具结果数、写盘是否成功；不满足就退回模型摘要，而不是带着空交接换窗。
6. **大工具输出在入口就截断并落盘。** ptc 的 maxChars 和 ref 机制、ctx-mod 的 `big-*.txt` 都是这个思路：上下文里只留头尾加编号，需要时再按编号或 offset 读。187 步里的大部分体积通常来自工具结果，这一项可能比折叠本身更能压住增长。
7. **把多步读查改合进一次 `run_code`。** 我们的 DS 长程题对照里，开 ptc 后轮数明显减少。轮数少，上下文增长就慢；遇到网关中途换号导致缓存失效时，损失也小。

## 4. DeepSeek v4.1 Flash 相关经验

- **价格**（`D:\ptcab` 成本脚本里用的口径，USD/1M）：未命中输入 0.14、缓存写 0.14、缓存读 0.0028、输出 0.28。**这组数字没有重新对照官方页核实**，用前请核对 https://api-docs.deepseek.com/ 。按我们的长程题实测，DS 单任务费用约为 Sonnet 的 1/20。
- **思考档位**：delegate 的 flash 和 pro 是同一个模型 deepseek-v4.1-flash，只是 effort 不同（flash=low，pro=high，可选 max）。长程题 ptc 组各跑 10 次：low 86.0±5.3、high 86.4±7.1、max 86.6±5.2，均分没有差别；max 的思考量约为 low 的 2.5 倍，轮数多约 50%。所以默认用 low。
- **能力边界**：深层隐藏 bug（H2 题）DS 0/4、Sonnet 3/5。但先让 DS 做只读诊断再实现，DS low 只读诊断 3/3 找到。DS 的格式和边界错误比 Sonnet 多，需要按规格逐项验收。
- **缓存**：
  - 走 workbuddy 网关时，网关会在中途换号，缓存随之失效。这是我们观察到的主要缓存损失来源，轮数越少影响越小；
  - 在 delegate 环境里把 claude CLI 指向 `claude-haiku-5-5`，实际返回的 `message.model` 是 deepseek-v4.1-flash。特征是 `cache_creation` 为 0、`cache_read` 固定 384（或 0），而 `modelUsage` 的键仍写着 claude 模型名。所以 DS 链路上 usage 里的缓存字段不能当真实命中率用；要测缓存，请看网关或官方 API 的原始响应。
- **replay 兼容性**：
  - 我们经 CPA（Anthropic 协议转换代理）跑 DS/GPT 时，流式 `message_start` / `message_delta` 的 `usage.output_tokens` 会正常回传，runner 运行中就能读到实时输出数；
  - CPA 源码审查（2026-10-25）结论：工具调用、tool_result、SSE 事件链有明确转换；**thinking 签名、prompt caching、server tools、count_tokens、Anthropic beta 头跨协议时可能降级或丢失**。如果 DSH 要回放含 thinking 块的历史，跨协议时要预期签名不保真，最好在回放前剥掉或重建 thinking 块。这一点没有专门做过回放实验，只是源码层面的判断；
  - runner 不保留 thinking 内容（EFF-SIGNAL 报告提到）。如果需要事后分析思考，得另外落盘。
