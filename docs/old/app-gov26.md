
**25. 自述类断言必须附回读读数。** 实测（tier 0 · 本轮第 9 处错）：我向 verifier 声称「**我把这三张一并推进到了 `verifier-review`**」（指 `task-22`/`task-23`/`task-24`），而**实际只推进了 24** —— 22/23 停在 `member-check` ⇒ **对方白撞一次相位门**。成因：同批里我对 24 用了「complete + advance」模板、对 22/23 只用了「complete + release」，**模板不一致而我未回读**。
   · ⇒ **自述类断言（「我做了 X」）比别人的读数更不可信，因为它看起来不需要证据。** 与 §5.14-21（断言「谁违反了 X」前必须同轮实读）同族，但方向相反：那条防的是**指认别人**，这条防的是**自述完成度**。
   · ⇒ 纪律：**凡自述「已推进 / 已更正 / 已提交 / 已通知」，必须附该动作的回读读数（revision / phase / commit / 回执 id）。**

**26. `jobId` 不是耐久载体；耐久载体是 job 的「写出路径」，应在启动时声明。** 实测（lead-rig）：harness 重启后 `job_output` 报 `unknown job pwsh-2493`、`job_list({})` 返回 `[]`，**而 run 活着** —— 最新批次文件写在**其读取前数秒**，进程仍在跑，服务端 java 仍占用，**m0 oracle 全程未被触碰**。⇒ **从 jobId 读不到结果，不等于 job 没在产出。**
   · ⇒ 纪律：**长任务在启动时就要声明它的「写出路径」**（产物落盘位置），并以**该路径的字节/时间戳**作为存活性与完成度的证据；`jobId` 只作便利句柄，**不得作为唯一证据**。

**27. 不得把「计算投影」当作「存储对象」来断言其状态。** 实测（lead-rig）：控制面里 `"status":"derived"` 出现 **0** 次、`"reason":"waiting-dependency"` 出现 **0** 次，而 `waiting_list` **确实返回**这类条目 ⇒ **derived 条目没有存储行，是每次读取时重新计算的投影**；`waiting_set` 写的是**存储行**。⇒ **「显式 vs derived」是两种不同机制，不是同一对象的变体。**
   · ⇒ 纪律：**断言某对象的状态前，先确认它是「存储的」还是「投影的」** —— 对投影对象做「写入 / 解除 / 修订」类操作，或在没有存储行的前提下推演它的状态机，都是**层级错误**（与 §5.14-4「不得把读到的输出形态当输入形态」同族）。
