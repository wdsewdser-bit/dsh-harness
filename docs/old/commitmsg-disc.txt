docs: 两条条款 —— 「判据必须在它所要分开的候选集上被验证（git status 受 stat 缓存支配，无判别力）」+「声明可观测者，不要声明本应产生它的设置」

- 实证一：安全阀判据「git status --porcelain 为空」在五个互相矛盾的候选上全是 0（采纳的 A0 内容级改写 0/889；A1 155；A2 2 均为二进制；A3 415；A4 0）⇒ 失败集为空 ⇒ 不是判据。机制：git status 受索引 stat 缓存支配，回答的是「是否需要重新 stat」而非「规则会写什么」。
- 纪律一：一条判据必须在它所要分开的候选集上被验证；对最好与最坏候选读数相同的不是判据。凡「某规则会不会改变内容」的判据必须用内容级读数（逐 blob / hash-object），不得用 git status。
- 正面样本：成员主动披露原判据的仪器局限（而不是悄悄换更弱的），并同时给出替换仪器与逐候选读数 ⇒ 下级的仪器检验是上级判据错误的第一道闸。
- 实证二：条款原要求配置身份「至少含 core.autocrlf」，verifier 锐化：只声明取值不够，应声明 worktree 实际行尾 —— 因为 config 值 ≠ worktree 实际行尾（clone 时 -c 不落盘，后续 checkout 按系统值物化）。
- 纪律二：声明可观测者，不要声明本应产生它的设置；配置身份本身也要以可观测形态具名（git ls-files --eol / 字节数 / CR 计数）。
