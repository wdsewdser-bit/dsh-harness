
**§5.14 补：`commit_sha_scope.commits` 的元素形状冻结（2026-09-28 · verifier 指出 + lead-rig 承认缺口 · tier 0 收编）**
- **缺口**：前述三件套冻结了 `meta.commit_sha_scope` 的**位置 / 类型 / 嵌套（逐 kind 的 5 个顶层键）**，但**未冻结 `commits` 的元素形状**。
- **实测后果**：world 的包用**裸字符串** `["19974d7e…"]`，而本会话其余所有包（含 lead-rig 自己的）用 `[{task, sha}]` ⇒ **消费者按 `commits[i].sha` 取值会得到 `undefined`，且不会报错**。
- **⇒ 裁定（补）**：`commits` 的元素形状**冻结为 `{task, sha}`** —— `task` = 卡 id（字符串）、`sha` = 40 位小写 hex。**裸字符串不合格。**
- **若要允许两种**：则**必须由包内显式声明元素形状**（与「形态差异必须由**两侧都必填**的显式标识承载，绝不靠字段缺席」同一条）。
- ⇒ **一般化**：**冻结一个容器，还须冻结它的元素形状** —— 与「冻结一个对象，还须冻结它的位置与嵌套」是**同一缺口在两个层级上的形态**。

**33. 「可推得」不等于「已声明」。** 实测（lead-rig 用**别人的清单**审**自己的载体**）：它用 verifier 的五项清单审自己的 `evidence-102441dd`，**4 项已显式声明**（Ordinal 整行升序 / `|` 分隔 / LF + 一个尾随 LF / UTF-8 SHA-256），**唯独「路径基准」未声明** —— 它只是**可从行内路径推得**（`55e91ef4…:tests/fixtures/…` ⇒ 仓根相对）。值**仍精确复算命中 `41ac08dd…`**。⇒ 已补**显式**声明：**`PATH_BASE = 仓根相对（路径所属工作树的根）`**。
   · ⇒ 为什么这是缺陷：**猜错基准的消费者会得到不同的值，且分不清是载体错还是自己读错。** ⇒ **「可推得」只对「已经知道答案的人」可推得**；载体必须让**不知道答案的人**也能复算。
   · ⇒ **标准五项清单（载体声明的最小集）**：**路径基准 / 排序键 / 分隔符 / 行尾 / 判别长度（或编码）** —— **五项逐项显式声明**，不得留任何一项「可从上下文推得」。
   · ⇒ 方法论上更值得记：**这条缺陷是用「别人的清单」审「自己的载体」查出来的** —— 与「横向自比（收到别人的 nit 先问『我有没有同族实例』）」同族，但**更强**：**不止问「我有没有同族实例」，而是拿对方的判据清单逐项过一遍自己的产物。**
