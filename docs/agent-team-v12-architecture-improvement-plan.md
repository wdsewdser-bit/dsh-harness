# Agent Team v12 架构改进计划

> 状态：A-M 已完成代码、聚焦回归和真实 PTC 验收。2026-09-25 补齐 D/G/H：跨组决定多组长确认、验证配方与精确证据复用、fan-out 收益检查、自适应并发（shadow）、历史工时与置信度。最终状态、哈希和真实回执见 `agent-team-v12-implementation-ledger.md`。
>
> 压缩恢复后的第一动作：重新读取本计划及 `D:/dsh-test/docs/agent-team-v12-implementation-ledger.md`，确认当前阶段、已完成项、未完成项和下一步，然后才继续实施或验收。

## 1. 目标

把 Agent Team 从“靠角色提示词和成员自觉协作”逐步改为“提示词负责说明、控制面负责强制、证据负责验收”的可恢复协作系统。优先降低无效唤醒、重复上下文、重复测试和卡死恢复成本，同时保持现有会话、任务卡、Room 和权限状态可继续使用。

## 2. 设计约束

- 角色文件和 `AGENT.md` 是行为说明，不是权限边界；权限必须由工具和控制面校验。
- 静默消息不应隐式唤醒；需要对方及时处理时使用显式 wake。系统级提醒和巡检由独立规则触发。
- Transcript 不等同于持久决策；“有活动”不等同于“有进度”。状态转换必须有明确前置条件、操作者和证据。
- 硬门禁必须有可解释的拒绝原因及恢复路径；不能因计划错误、状态回退或重试而永久锁死。
- 先兼容现存会话与磁盘状态，再改变新会话默认值；迁移须可重复、可检查、可回滚。
- 成本指标需区分模型调用、等待、工具执行和返工，不能只用调用数推断效率。

## 3. 主要风险

1. 任务准入和状态分散在提示词、工具和看板中，成员可能在计划不明确、依赖未解决或写入范围冲突时开工。
2. 控制面持久化故障可能回退到默认/旧状态；审计错误被吞会掩盖状态损坏。
3. Room transcript 过长、旧消息重复注入；压缩后决策与未读消息游标不一定能可靠续接。
4. wake 语义、投递重试和系统提醒相互交织，容易出现延迟、重复或漏唤醒。
5. 压缩原因与里程碑、上下文压力、idle 等触发路径不够清楚，难以解释“为何压缩”。
6. 审查与测试可能重复、泛化，或缺少能证明交付质量的证据。

## 4. 分阶段计划

### A. 建立运行事实清单

- 由 Plugin Manager/运行时枚举生成只读清单，记录采集时间、运行实例标识、DSH 版本/profile、已启用插件及版本、实际加载入口文件的规范路径与哈希、插件来源和本地 patch 标识/来源。
- 对关键配置只记录非敏感字段及来源；密钥、token、认证头和可还原凭据不得进入清单、日志或差异报告。
- 对每项 Team 功能记录实际入口、状态来源及所有者（如 DSH 原生 Team 域或本地控制面）、状态存储位置、schema 版本、权限检查、唤醒/投递效果和恢复方法；域所有权未知时明确标记未知，不能合并或误读为同一状态。
- 将文档预期、磁盘配置/安装状态、运行时 Plugin Manager 实际加载状态及会话快照分层呈现，逐项对照并报告差异，例如“配置已启用但未加载”“加载版本与声明不符”“运行入口与文档路径不同”“patch 来源不明”“状态所有者/schema 未确认”。
- 清单注明每个字段的观测来源与可信度；运行时接口不可读、采集不完整或实例在采集期间变化时显式降级，不得将缺失证据推断为未安装/未启用。
- 在启动后和按需诊断时可重新生成快照，保留时间戳与差异摘要；它是由运行事实生成的诊断产物，不另造一份需要人工同步的权威清单。
- 修复前以清单确认修改对象与活入口；生成过程只读，不触发重载、迁移或状态写入。

验收：能从一个会话定位实际加载实现、插件/patch 来源和各状态存储及 schema；对文档、配置、Plugin Manager 与会话快照的差异可逐项追溯；报告不含秘密且不完整采集会明确标记。

### B. 任务准入与进度状态机

- 每张工作卡在执行前记录最小任务契约：目标/交付物、验收标准与证据、唯一 owner、write scope/worktree、依赖、风险等级和契约修订号。
- 统一生命周期：`proposed -> ready -> running -> blocked/review -> completed`。取消、失效和重开采用显式转换，不靠任意改 phase 绕过。
- `ready` 前强制检查 owner、scope、依赖、冲突和验收条件；依赖图拒绝循环，写入范围冲突要求串行或明确拆分。
- 将“正在运行/有心跳”与“产生可验证进度”分开记录；重复相同失败应形成有证据的 blocked，而非无上限重试或反复唤醒。
- 允许契约安全修订：owner 无有效 lease 时可提议扩大 scope 或更换计划；scope 扩展须审计、检查冲突并让执行者重新确认，不得静默改变已执行任务约束。
- lease 绑定 owner、卡、scope、worktree 和待审 SHA；过期、释放、转交和恢复均可查询。
- 共享、高风险、跨组或需求不清的工作要求 Room 协调；简单独立任务不强制开 Room。
- 拒绝信息说明阻塞条件和最短修复路径；仅限 tier-0 的操作应在工具说明和拒绝信息中明示。

验收：不完整任务不能进入 `running`；失败或崩溃后可从持久状态恢复；重新分配、扩 scope、重开及完成权限不会相互构成死锁。

### C. 控制面持久化与恢复

- 状态变更采用互斥锁、修订号/CAS、schema 校验和原子替换；并发写入不得静默覆盖较新的修订。
- 区分暂时读取失败、损坏状态和真正空初始状态。无法确认当前状态时进入只读/降级模式，拒绝状态变更，绝不构造默认空状态后继续写入。
- 保留带修订号的最后有效快照和损坏原件；自动保存快照不等于自动回滚，不能因读取失败自动用旧状态覆盖当前文件。
- 恢复前提供当前文件与快照的差异、各自修订号和可恢复范围；由 root 明确选择恢复目标。恢复须留审计记录，并保留被替换文件以便追查。
- 核心状态变更的审计事件必须与状态转换具备明确的一致性策略；审计写失败要可观察，不能吞掉后继续报告成功。
- schema 迁移提供版本、幂等性、迁移前备份和 dry-run 检查；本地控制面与 DSH 原生 Team 状态分清所有权，恢复时不得互相覆盖。
- 提供只读诊断和受控修复路径；恢复动作不默认清除新数据。

验收：模拟写入中断、并发更新、暂时读取失败、损坏 JSON 和旧 schema 时，不能静默丢状态或回退；root 能看到快照差异并显式确认恢复来源。

### D. Room：消息游标与决策记忆

- 将逐条 transcript、轮次摘要、待处理事项和已确认决策分成不同数据类型。
- Transcript 追加写入并保留来源；更正和新结论以新记录表达，不回写历史消息。
- 仅将明确确认的决策写入 durable decision ledger。记录决策 ID、来源消息 ID、适用任务/范围、责任人、状态、修订号和被替代关系；区分提议、已确认、被替代和撤销。
- 同组范围内由组长或 Room 主持人确认决策，主持人本身也是参与成员；跨组决定由所有受影响组长确认。只有冲突无法解决，或涉及全局优先级、权限和策略时才升级 root。
- 每个成员维护每个 Room 独立的已读消息游标。唤醒包只包含当前任务契约、适用的有效决策、游标之后的相关新消息和未解决事项，不重放房间开头的历史。
- 游标只在消息成功纳入成员上下文后推进；投递失败不得跳过消息。重试要幂等，避免重复注入同一批内容。
- Room 快照采用分页/增量读取；默认展示最新进展与决策，旧轮次可折叠。摘要有独立修订号，更新不能改写原始 transcript 或覆盖决策 ledger。
- 风险、问题、决策请求和已解决项有明确状态；普通讨论不能自动永久制造 unresolved。
- 讨论结束时生成结构化结论：决定、分歧、未决问题、owner、下一步和证据链接；压缩后从 ledger、任务契约和游标恢复关键共识。

验收：新消息可达、旧消息不反复注入；重启/压缩后能恢复最新决策、游标和未决项；历史仍可审计。

### E. 统一 wake 与通知调度

- 将显式定向 wake、静默投递、轮询提醒、idle-watch 和 all-idle 提醒定义为不同事件和策略。
- wake 记录目标、原因、优先级、去重键、投递状态和重试策略；同一原因重复请求可合并，不能因终态投递对象再转移成失败态而丢失。
- 为每个成员维护持久收件箱，逐条保存消息 ID、发送者、任务、优先级、原文和处理状态。收件箱消息不等同于 wake：静默投递继续保持静默，需要对方处理/回复时才显式请求 wake。
- 若同一成员已有待处理的 queued wake，新请求合并到该成员的待处理批次，在目标下一次 turn 一次交付批次摘要和逐条消息引用；原文始终可读取，紧急/高优先级项在摘要中突出显示。按消息 ID 逐条确认，只有成功纳入上下文的条目才推进游标；新到达的高优先级请求不得被旧批次摘要掩盖。
- wake 的默认语义是“排队到目标下一步处理”，不打断当前 turn、不撤销当前工具调用，也不改变 lease。root 和组长的角色文件、工具描述、返回值和审计事件都必须明确这一点；需要立即停止时只能调用独立且有权限检查的 `interrupt`。
- 返回值区分 `queued`、`delivered`、`handled`、`deduplicated`、`delivery-failed` 和 `rejected`；`queued` 只代表已可靠入队，不代表目标已经阅读或执行。
- 只有显式 wake 或系统规则可以唤醒；普通消息投递不触发全局检查。
- all-idle 按“停工 episode”记录：一次 episode 在仍无人工作期间至多提醒一次；出现新工作后关闭 episode，下次停工可再次提醒，不设跨项目终身上限。
- 定时巡检仅在至少一个 team 活跃时运行，并向 root 提供 team/任务状态摘要；无活跃 team 时停止调度。
- 冻结成员不进入普通活跃列表和创建配额；可从专用冻结视图查询，并保留恢复路径。

验收：定向 wake 准时抵达且不唤醒无关 team；待处理 wake 合并时消息 ID/原文/优先级均不丢，游标仅在成功注入后推进；静默消息不唤醒；投递错误可区分可重试与业务拒绝；每个停工 episode 恰好提醒一次。比较改动前后的唤醒次数、消息处理延迟、未处理积压和重复注入率。

### F. 压缩触发与续接

- 将里程碑状态和压缩任务作为两个独立的持久状态机。`done(milestone_id)` 原子地确认该里程碑完成并创建幂等压缩任务；工具调用本身不立即压缩，也不结束当前 turn，并明确告知模型本轮仍可设置下一里程碑。
- 下一次 `set` 创建新里程碑记录，不能覆盖已完成里程碑或删除压缩任务。压缩任务按 `queued -> waiting_for_handoff -> ready -> running -> completed/failed` 追踪，并绑定 milestone ID、上下文修订号和触发原因。
- 普通压缩必须等当前 turn 到达安全边界，并且下一里程碑已持久化，或已明确记录“无下一里程碑”后才执行。压缩快照保留下一步目标、验收条件、依赖、owner/scope、第一步、有效 Room 决策、未决事项和游标。
- idle 仅作为待处理压缩任务的安全执行点，不是独立压缩触发原因；上下文压力、人工请求和 provider 错误恢复各自记录独立原因。
- 若紧急上下文压力必须越过交接门槛，压缩仍须保留 `handoff_pending` 标记；恢复后优先提醒补齐下一里程碑，不能将未完成交接误报为完成。
- 只有显式 milestone 状态可触发 milestone 压缩；压力阈值有独立配置和可见原因，不能伪装成 milestone。
- 留存最近必要交互、未完成任务、有效决策、未读 Room 游标和 lease；大型工具日志按类别裁剪，同时保留最近若干条及错误/证据摘要。
- 压缩前后提供原因和摘要校验；失败时保留原上下文和可重试任务，不丢待办或重复完成状态转换。

验收：覆盖同一 turn 内 `done -> set`、done 后显式无下一步、idle 到达交接完成前、紧急压力绕过和压缩失败重试；能解释每次压缩的触发与执行时机，且不丢任务 owner、决策、未读消息或下一步。

### G. 交付审查与成本/质量度量

- 每条验收标准映射到检查方法、证据和负责角色；没有覆盖证据的验收项不能标为已验证。
- 组员只做与自己变更直接相关的快速局部检查，提交变更范围、风险、结果和证据，不重复跑其他成员已覆盖的完整测试。
- 组长合并同组及跨组报告，去重测试项、标记共享接口和冲突风险，再提交一份统一审查包；审查员不需要从散落的 agent 消息里拼接状态。
- 审查员按验收标准和风险设计有限、针对性的验证矩阵；不以测试数量作为质量指标，也不跑与变更无关的泛化测试。覆盖高风险项后应汇总发现与残余风险，不声称能穷尽所有可能问题。
- 交付绑定 exact SHA、运行环境、测试命令/结果、截图或日志证据；集成后重新验证集成 SHA，不把子分支成功当作最终通过。变更 SHA 后只重跑受影响的检查，除非风险评估要求扩大范围。
- 区分静态检查、单元/集成测试、真实用户路径和视觉检查；视觉审查覆盖实际相关的方向与状态，并用网络响应、资源解码、透明度/材质诊断等证据排查资源缺失，不能只凭单一视角外观判断。
- 建立按变更类型复用的验证配方（例如 API/状态机、持久化迁移、UI/视觉、构建/集成），但每次仍须映射到本任务验收条件、风险与 exact SHA；配方提供检查模板，不得把不相关测试机械套用到任务上。
- 建立可查询的验证证据登记表，按 exact commit/tree hash、相关环境指纹、命令/参数和 fixture 记录验收项、执行者、时间、结果及原始日志/截图的位置与校验值。先查是否已有完全匹配的证据，再决定是否重跑；只复用覆盖当前验收条件且输入和环境均匹配的记录。
- 证据查询默认只返回摘要和引用，审查员按需打开原始材料，避免把大日志反复塞进上下文。代码、依赖、profile、运行环境或测试输入变化时，只将受影响的证据标为 stale；不得仅凭旧的 pass 结论复用，也不得因缓存命中隐藏失败记录。
- 记录 token、等待、返工、重复测试和缺陷逃逸，按任务类型比较质量与成本；不设没有根据的固定 token 目标。

验收：每项完成声明都对应验收标准与证据；审查包精简、责任明确并覆盖高风险失败模式；完全匹配的证据可复用，代码/环境/输入变化后相关证据会失效而无关证据保留；指标能揭示重复测试、过期误用和返工。

### H. 事件驱动调度、停滞诊断与任务成本护栏

- 在任务契约和状态机（B）、持久化/事件记录（C）及 wake 语义（E）稳定后，增加可重建的 ready queue。队列以任务状态、依赖、负责人资格、lease、worktree 与 write scope 冲突为输入；队列是派生视图，不能成为另一份互相矛盾的任务事实源。
- 仅对已批准且依赖满足的任务进行排队/派发；新建或改写目标、验收条件、权限和 scope 仍走原有批准门禁。任务完成、阻塞解除、lease 释放或成员可用性变化时，由事件触发重新计算；周期检查只作漏事件的低频兜底，不让 agent 高频轮询状态。
- fan-out 前检查每个子任务是否有独立交付物、验收条件、owner 和不冲突的 scope，并比较可并行工作与拆分、沟通、集成的预期成本。没有独立验收或单人即可快速完成的工作，建议留在当前 owner；依赖紧密或收益不确定时建议串行或先做有界试点。估算优先引用历史同类任务；数据不足时明确标为未知，不设固定任务规模/收益阈值。
- 收益检查是可解释的派发建议，不自动生成 team、不绕过审批或权限门禁；组长可基于理由覆盖，并记录预期收益与实际用时、协调调用、返工和质量结果，用于校准后续判断。
- 调度优先选择可并行且互不冲突的工作，不按 team 数量盲目拉满并发；同一文件/scope/worktree 有冲突时串行化或明确分配隔离工作区，并解释暂不可派发的原因。保留优先级与公平性，避免低优先级任务永久饥饿和计划反复重排。
- 根据 ready queue 中独立可派发任务、实测吞吐/等待、provider/tool 错误、scope 争用和返工趋势，调整后续新任务的并发派发建议；尊重已配置配额与资源约束，不臆测供应商隐藏并发上限。先影子观察，再缓慢调整并设置滞回/冷却以避免反复震荡；出现 429、超时或冲突上升时优先减少后续派发，不自动中断在执行任务。
- 并发控制只调度已有批准且已分配的任务，不自动 spawn/freeze/reassign 成员，不改变任务权限、scope 或 owner；建议目标并发及触发依据可见，组长可覆盖并留审计记录。
- 在符合资格且依赖已满足的任务中，按依赖图识别关键路径及能解锁多个下游任务的瓶颈，作为派发排序建议；剩余工时优先参考同类任务历史数据并标注置信度，没有历史依据时明确显示未知，不伪造精确预测。排序须可解释、可人工覆盖，只改变既有批准任务的优先顺序，不自动改目标、scope、负责人或打断成员。
- 将“等待依赖/外部结果/排队 wake”“权限或 scope 阻塞”“重复失败或无进展”“疑似工具/会话挂起”分成不同停滞类别。每类有可观察的进入条件、计时/重试策略和责任人；只把需要决策的阻塞升级上级，等待中的任务不反复唤醒模型。
- root/组长默认获得聚合状态和例外队列，而不是反复逐个查询成员。系统提示必须包含具体任务、阻塞证据、最后进展、可选动作及需要谁决定；不得仅凭静默时间就判定成员偷懒或自动中断。
- 调度动作具备幂等键、重试上限/退避、审计记录和人工暂停入口；故障恢复时从持久事件重建队列，不重复派发已领取任务。先以影子模式记录“建议派发/实际派发差异”，验证正确性后再启用自动排队。
- 按任务记录模型/工具调用投入、等待与重试，以及已产生的可验证产物/验收进展；用任务类型和风险配置软预警条件，识别“投入持续增加但无新证据、里程碑或可合并产出”的情况。预警应附趋势和证据，供组长检查是否拆分任务、修正方案、换负责人或批准继续。
- 成本预警本身不等于失败，不设置可能误伤长任务的全局硬 token 上限；不得仅因超过软阈值自动终止 turn、撤销 lease 或丢弃已有工作。需要调整目标/预算或中止时，走明确的组长决策和独立 interrupt 权限路径，并保留已完成产物与状态。

验收：依赖完成或 lease 释放后，符合条件的任务无需 root 高频轮询即可进入队列；有 scope 冲突时不发生并发写入；等待类状态不产生多余唤醒；fan-out 建议能解释独立交付与协调成本依据，且人工可覆盖；并发调整依据可见、变化稳定且只影响后续派发；关键路径排序依据和升级对象可解释；重启恢复后不重复派发。成本预警能指出投入与进展趋势，且不会自动中断任务。以真实任务比较关键路径等待时间、整体交付耗时、吞吐、无效唤醒、协调成本、冲突/返工率、无进展投入和总 token 成本。

### I. 集成事务与合并后置验证

- 每次集成先创建持久、幂等的 merge operation，记录 source/target ref、source commit/tree、target 基准 SHA/tree、worktree 标识与路径、合并策略、owner/lease/scope 和操作 ID。执行前验证权限和目标状态；同一 target 的并发合并须串行化，若基准在操作期间变化则重新预检或拒绝，不能悄悄基于过期目标继续。
- 预检清点 tracked 修改、untracked、ignored 与生成文件，按配置分类报告；不得自动删除或覆盖文件。只有显式策略允许排除的项目才能不阻断，并须在结果中列出。
- 操作状态持久记录为 `prepared -> merging -> verified -> task-advanced`，另有 `blocked/recovery-needed`。若进程在 Git 更新与任务状态写入之间崩溃，恢复时先对照操作 ID、refs 和 tree 重建实际结果，不盲目再次 merge；任务状态写入须幂等。
- 成功判定以 Git 实际后置条件为准，而不是工具返回的 `merged: true`。按合并策略验证 source 内容确已进入 target，并记录实际 target SHA/tree 与证据；常规 merge/fast-forward 检查提交包含关系，squash 等策略使用对应的 tree/patch 校验，不强套单一 ancestor 规则。
- 只有后置条件验证成功后才允许推进 phase/complete。冲突、SHA/tree 不符或状态不确定时保留 refs、worktree 和现场，标记恢复待处理并说明差异；不得自动 reset、清理或回滚用户数据。

验收：覆盖正常 merge、fast-forward、配置允许的 squash、冲突、dirty worktree、目标并发变化、工具误报成功及 Git 更新后状态写入前崩溃。不得出现未验证就推进任务、重复 merge 或静默丢文件；恢复可根据 operation ID 判断继续、已完成或需人工处理。

### J. 统一上下文组装与 token 预算

- 每次模型调用从权威状态源组装一个可审计的 context pack，而不是由多个插件各自重复拼接整段状态。来源包括角色/权限约束、当前任务契约、owner/lease/scope、适用的有效决策、游标之后的新消息、未决事项、最近相关工作和验收证据引用；派生摘要不能取代其权威来源。
- 每个上下文条目带稳定来源 ID、修订号、适用 team/task、产生时间或新鲜度、优先级、保留类别及估算 token 成本。组装前按目标成员的可见范围和任务关联过滤，避免跨 team 泄漏、过期状态或无关历史。
- 按来源 ID/内容哈希去重；大型日志、工具输出和证据优先使用可访问的引用与定向摘要，不在每轮重复注入全文。摘要须保留来源和定位信息；模型需要原始内容时再按引用读取，不能把有损摘要伪装成完整证据。
- 对静态约束、当前任务状态、增量消息和可选背景资料分层管理；未变化的内容不因无关事件反复重写，变化项优先按修订/游标增量加入。保持稳定输入只能减少客户端重复组装与内容漂移，不承诺或控制供应商服务端缓存命中。
- 预算根据运行时可确认的模型上下文能力、任务风险/复杂度及输出预留动态分配；不得硬编码未经确认的上下文长度或制造虚假的精确 token 预算。先以影子清单记录当前每轮实际注入、重复项、遗漏项和成本基线，再逐步启用去重与分层裁剪。
- 超预算时按可解释的顺序处理重复全文、较旧原始日志、已被新版本取代的背景及低相关可选资料；保留权限/安全约束、任务验收、当前 owner/scope、有效决策、尚未处理的新消息、未决阻塞和关键证据索引。裁剪结果必须记录被省略的来源及原因，不能静默丢弃必需信息。
- 若必需上下文本身仍无法容纳，不得把不完整 context pack 当成完整输入继续执行；进入明确的 context-budget-blocked/压缩续接路径，汇报冲突来源和所需动作，并与 F 的压力压缩/交接状态衔接，保留待续接标记。
- 为每次调用记录轻量 context manifest：已包含/排除的来源 ID 与修订、过滤/裁剪原因、摘要及估算 token 分布；优先保存引用和校验值，不复制整份大日志。能取得供应商实际 usage 时用于校准估算，取不到时明确标为估算值。
- 测试重复状态、多版本互相矛盾、过期 Room 消息、大型工具输出、必需材料超预算、成员权限不同及压缩/恢复交错等情形；比较重复输入比例、上下文构建开销、关键事实/决策召回、任务成功率、返工和实际 token usage。任何节省都不得以漏掉关键约束或降低交付质量换取。

验收：同一来源不会因多插件重复拼接而重复进入上下文；每个有效决策和待处理消息可追溯到来源及修订；过期或越权材料被排除且有记录；超预算时不静默丢必需信息；与基线相比重复输入和上下文成本下降，同时关键事实召回、任务成功率及质量不下降。旧会话可继续读取，无法解释的旧格式不被静默删除。

### K. 跨 profile 能力清单与契约一致性

- 基于 A 阶段运行时事实清单，为每个目标 profile 生成只读能力矩阵，记录插件 ID/版本、实际入口与哈希、已安装/已启用状态、声明能力、可调用工具及 schema、持久化 schema 与关键状态/消息语义。清楚区分“已安装”“已启用”“对外声明”和“真实可调用”，不得仅凭配置或文档推断功能可用；报告不得包含密钥。
- 对多个 profile 都声明支持的同一能力，维护一套规范化契约和共享 fixture，分别运行工具 schema/参数校验、权限拒绝、状态转换、消息投递/wake、Room 游标、重试幂等及旧会话/旧 schema 兼容测试。比较业务语义和后置状态，不要求无意义的逐字相同输出。
- 允许 profile 间有意存在能力差异，但差异必须在矩阵中明确标为 unsupported/不同语义，并有对应测试或明确的兼容边界；不能把未测试、插件未安装或运行时不可达记成通过。目标 profile 缺少必需能力时应在升级/发布门禁前失败并指出缺项。
- 契约测试随 B-J 各阶段的功能契约逐步补齐；用隔离 fixture 或临时状态验证，不直接污染用户会话。跨版本升级前对候选 profile 生成能力矩阵差异，先跑受影响的契约和旧会话兼容测试，再逐步启用；记录精确 profile、插件版本、入口哈希、schema 版本、测试输入和结果。
- 升级失败时保留差异报告和原状态，不自动删除/重建会话或覆盖持久数据。需要恢复时依据兼容性检查和明确的恢复流程处理，不能把“另一个 profile 测试通过”当作失败 profile 已验证。

验收：被声明为等价的能力在每个目标 profile 上通过同一组契约；有意差异均可见且有测试说明；未安装/未启用/不可调用/行为不符可以被区分；profile 或插件升级造成的能力漂移在启用前被发现；兼容测试不得静默丢弃旧会话字段或覆盖用户状态。

### L. 真实故障回放与回归用例库

- 从已确认的真实事故中提取最小、脱敏、可复现的 fixture：记录隔离的初始状态、规范化事件顺序、profile/插件/schema 版本、可控时钟与故障注入点，以及应保持的状态不变量。不要直接保存完整私有会话、密钥或大段工具输出；敏感/大内容优先存最小必要字段、摘要和校验值。
- 使用临时状态目录、模拟时钟和 fake provider/tool/dispatcher 驱动真实控制逻辑；默认不发起真实模型请求、不连接生产供应商、不读写活动会话。fixture 无法脱离真实服务验证的部分需标为 live-only，不伪称已由本地回放覆盖。
- 断言业务后置条件和安全不变量，例如消息不丢/不重复、游标不越过未投递消息、跨会话状态不串用、状态迁移幂等、失败重试不重复派发、未验证交付不推进完成。避免依赖易变的自然语言全文快照；模型生成差异用结构化事件和可验证产物表示。
- 事故只有在根因和最小复现步骤经核实、敏感数据完成清理、预期不变量明确后才能进入正式回归库。保留来源事故编号/证据引用及 fixture 版本；后续修复必须能证明旧 fixture 在修复前失败、修复后通过。未证实假设不得固化成产品规则。
- A/K 建立运行与 profile 基线后先搭建回放框架；随着 B-J 状态和工具契约落地，逐步加入已确认故障 fixture，并把适用的跨 profile 用例复用于 K。每次升级按影响范围选择性回放；测试结果绑定代码/入口哈希、profile、fixture 版本及运行参数。
- 回放失败时保留初始状态、事件序列和差异报告以便诊断；测试隔离必须能证明没有触碰活动会话、真实消息投递或用户文件。真实会话验收仍是独立证据，不得用模拟通过替代必要的端到端验证。

验收：关键历史故障有可重复的最小 fixture；同一版本/输入可确定性重放；修复前失败、修复后通过的证据可查；回放默认无真实 provider 调用且不改活动状态；敏感内容未进入 fixture；升级后仅受影响的回归用例被标记和执行，模拟与真实验收边界清晰。

### M. 跨链路关联追踪与运行可观测性

- 基于 C 阶段的权威事件记录扩展关联信息，不另建会与任务/Room/wake 状态冲突的事实源。为一个工作流建立可传播的 correlation/causation 标识，将 task/team/session、wake 请求、收件箱 message ID、Room message/cursor、turn、tool call、状态修订及集成 operation ID 按因果关系串联；有供应商请求 ID 时记录其引用。
- 对投递链路分别记录并定义 `requested -> queued -> dispatched -> delivered -> injected -> acknowledged/handled` 及 `rejected/failed` 等状态。不同阶段不能互相冒充：入队不代表送达，送达不代表进入模型上下文，进入上下文不代表已处理。记录每次尝试、重试原因、时间/序号和结果，缺少后续事件时显示为观测断点，不推断为成功。
- 结构化事件至少包含事件 ID、因果/关联 ID、源状态修订、profile/插件版本与入口哈希、actor/tool、事件类型、结果类别、错误码/重试信息和时间信息；同时用单调序号或因果边辅助排序，不能只依赖跨进程墙钟判断先后。可取得时记录调用耗时和 provider usage，估算值须显式标注。
- 提供只读的单任务/成员/消息诊断时间线，能从一条 wake 或 Room 消息看到其排队、投递、注入、处理及对应状态变化，并定位最后成功阶段、等待时长和失败原因。聚合摘要供 root/组长查看，默认无需唤醒被追踪成员；追踪数据本身不改变调度、权限或 wake 行为。
- 遵循最小化和访问控制：默认不记录完整 system prompt、私有对话正文、密钥或不必要的文件内容；用稳定 ID、必要状态字段、错误摘要和受控证据引用代替。高频事件可压缩/聚合，但不能采样掉重建关键状态机所需的转移；按明确保留期清理诊断元数据并保留必要审计引用。
- 将经过脱敏和验证的关联时间线作为 L 阶段最小故障 fixture 的候选来源；fixture 仍须独立确认根因和最小复现，不能把整条生产 trace 原样复制进回归库。D/E/F/H/I 和 K 的诊断与验收逐步传播这些关联 ID。

验收：可从 task/wake/message/turn/tool/merge 任一已知 ID 找到同一因果链及每阶段结果；能区分 queued、delivered、injected 和 handled，并指出断点而不把等待误判为失败/成功；诊断查询不触发 wake、不读取越权内容、不改变运行状态；事件排序和来源版本可审计；不保存完整私密对话或密钥，且关键状态转移不会因采样丢失。

## 5. 推荐实施顺序

1. A 运行事实清单，明确活版本和状态边界。
2. K 跨 profile 能力矩阵先建基线；契约测试随 B-J 的功能契约逐步补齐，并作为对应 profile 升级/启用门禁。
3. B 任务契约与状态机，先定义状态和权限契约。
4. C 持久化与恢复，确保硬门禁不会因存储故障制造死锁。
5. M 建立跨链路关联 ID 与只读诊断时间线；事件来源以 C 的权威记录为准。
6. L 搭建隔离回放框架；fixture 随 B-K 契约、M 时间线和已确认事故逐步加入。
7. D Room 决策 ledger 与消息游标。
8. E wake broker 和停工 episode 通知。
9. F 压缩触发分类与续接。
10. J 统一上下文组装，先影子记录上下文清单和基线，再逐步启用去重/分层裁剪。
11. H 事件驱动调度与停滞诊断，先影子观察，再按验证结果逐步启用。
12. I 集成事务与合并后置验证，先只读预检和故障注入验证，再启用受控合并。
13. G 交付审查和成本/质量验证；验证配方与证据登记表按任务类型逐步沉淀。

每阶段先做只读盘点和兼容性测试，再实现迁移；已有会话须可继续，不要求一次性重置状态。跨阶段 schema 变更先定义兼容读写策略。

## 6. 全局验收

- 老会话数据可读取、迁移和回滚；未知字段不被静默丢弃。
- 权限拒绝指出缺少的条件和授权角色，不泄漏绕过方式。
- 任务、Room、wake、lease、压缩均可由事件和状态重建关键时间线。
- 通知、迁移、完成动作具备明确去重/幂等规则。
- 覆盖并发写、投递重试、成员崩溃/恢复、Room 增量读取、压缩续接和 worktree 脏状态等定向故障测试。
- 用短期真实会话验证 token、等待时间、返工率和质量，不以模拟结果替代真实运行验收。

## 7. 不在本计划内

- 本计划本身不授权改运行代码、重启 DSH、清理会话或迁移运行状态。
- 不把所有协作强制改成 Room；独立低风险工作保留轻量路径。
- 不给模型无限权限；提权、scope 扩展和恢复操作仍需最小权限、时限和审计。
- 不把单次测试或单个会话观察泛化成全局结论；先确认 profile、版本和活文件。

## 8. 讨论记录

- 用户已同意纳入“任务准入与进度状态机”，作为阶段 B；后续阶段顺延。
