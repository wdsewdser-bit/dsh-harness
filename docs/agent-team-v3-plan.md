## 1. 大阶段 + 阈值提醒 + 压缩（本轮核心）

### 1.1 要解决的问题

- 原生压缩只在窗口压力阈值触发，时机随机，可能切在任务中间。
- 上一版用 `todo_write` 当触发点：**两个致命问题** —— 会话结束 todo 就清空；实测主会话 `todo/write` **0 次**，模型根本不用。
- 压缩后模型失忆，不知道自己干到哪。

### 1.2 设计

**大阶段（milestone）= 每个 agent 自己的一个语义边界。**

| 项 | 规则 |
|---|---|
| 槽位 | **独立**，不进团队任务板（避免污染任务完成率与 CAS 权限） |
| 设置权 | **只能设自己的**：主会话只设自己的，组长 1 只设组长 1 的，组员 1 只设组员 1 的。**代码强制** |
| 内容 | 阶段名 + **完成判据**（「当 X 通过 Y 命令时算完成」，不是「把传送门做完」） |
| 上级 | **可读不可改**：tier 0 看 tier 1，tier 1 看自己的 tier 2 |
| 同级 | **可读**：同组成员互相可见 |
| 打勾 | 由**设置者自己**打，别人不能代打 |

### 1.3 阈值提醒（幂等，不依赖模型记性）

- 默认阈值 **0.2**（1M 窗口 = 20 万 token）。
- 到 0.2 注入提示：告知当前上下文用量，要求设置一个「不会影响当前任务直到完成为止」的大阶段。
- **每再涨 0.1 重新提醒一次**（0.2 / 0.3 / 0.4 ...）：模型忘了就再提醒，不需要模型记住。
- 提醒本身很便宜（一段文本），比压一次摘要便宜得多。

### 1.4 压缩执行：打勾上膛，idle 击发

**关键技术约束**：`compactNow()` 要求 agent **idle**（否则抛 `busy`），而打勾发生在**回合内**。所以不能在打勾时直接压。

```
打勾  ->  标记 '该压了'   （回合内，只上膛）
agent/status -> idle  ->  检查标记，有则 compactNow()  （击发）
```

- **语义来自打勾**（里程碑真的完成），**时机来自 idle**（引擎允许）。两个信号互补。
- 事件依据：`agent/status` 载荷 `{ agent, status }`，`status ∈ {idle, running}`，定义于 `dsh-agent-loop`。

### 1.5 硬阈值兜底（**不可省略**）

提醒解决「遗忘」，不解决「就是不打勾」。所以：**到 0.75 不管打没打勾，idle 时强制压。**

### 1.6 静默上报（**必须不唤醒**）

阈值提醒触发时把上下文情况报给上级，**但绝不能让上级被唤醒**：domain 的 `send(message, target, wakeup)` 本来就带 `wakeup` 参数，用静默投递。

- 理由：一个 1M 上下文的组员从 0.2 到 0.8 触发 7 次提醒，3 个组员 21 条，每条都把组长拽起来 —— 正面撞上第 7 点「别老唤醒主会话」。
- **只有两种情况真正唤醒上级**：① 到硬阈值还没打勾（真出问题）② 大阶段打勾（交付完成，该验收）。
- 上报内容：token/窗口占比、大阶段与完成判据、已完成到哪、下一步、**是否已打勾**、卡了多久。

### 1.7 压缩后不失忆

- 大阶段 + 进度 + 下一步写进**动态 system prompt 段**（每轮重建，**压缩打不到它**）。
- 任务看板作为补充视图：压缩后模型读看板能恢复「当前进度 + 下一步任务」。

### 1.8 验收

- 单元：只能设自己的大阶段（跨人设置被拒）；上级只读；同级只读；打勾后 idle 触发压缩；未打勾到硬阈值强制压；提醒在 0.2/0.3/0.4 各触发一次且**幂等**；上报**不唤醒**上级。
- 真实：跑一次长任务，确认压缩在里程碑边界发生、且压缩后模型能说出当前进度。

## 2. 第 3 点：组长不会用打断（**根因已实证**）

### 实测真相

组长会话里**没有一次 `interrupt_agent` 调用**。它用 `send_message(「立即停止当前任务」)` 代替，并把这次调用标注成「打断组员并冻结其写入范围」。另一个组长反复纠结「要不要 interrupt A1」，最后选「发消息催」，理由是「interrupt 会丢工作」。

**问题**：`send_message` 投给 running 成员只是「投递到最近一步」，**不会停止它当前的工作**。组长以为停了，组员还在跑。效果上等于「组长没有打断权限」。

### 修复

- 角色文件与 POLICY 明确：**打断是你明确拥有的权力，该用就用**；`send_message` **不是**打断手段。
- 写清判据：发现偏离 → **立刻 `interrupt_agent`**；只是慢 → 发消息问，不要打断。

## 3. 第 4 点：交付前核对看板

主会话交付前**必须**核对看板：是否全部 completed。
- 没完成 → 判断是**组长忘勾**（实际做完了）还是**真的没完成**。
- 忘勾 → 退回组长补状态；真没完成 → 退回返工。
- 依据：portal 截图里 G1 待处理 / G2G3 进行中，而组长实际已交付。

---

## 4. 第 5 点：同级与同组交流

- 现状：369 条消息里，**组员→组员 0 条**，只有上下级。
- 目标：同组组员之间可互相 `send_message` / 查看对方进度与大阶段，协调接口时不必事事经过组长。
- 同级组长之间同样可交流（跨组接口）。
- 硬约束保持：同级**可说话、可看，但不可互相打断**。

---

## 5. 第 6 点：审查员合并交付

**现状问题**：审查员被 43 条消息反复唤醒，频率过高。

**目标流程**：
```
3 个组长都跑完并互相沟通  ->  tier 0 统一交付给审查员
  ->  审查员统一审查  ->  汇总一份清单发回组长
```
- 硬约束：交付给审查员**只有 tier 0 能发起**，且要等各组长都报告完成。

---

## 6. 第 7 点：主会话唤醒收敛

- 现状：主会话被 91 条消息唤醒。
- 目标：**只有真正需要主会话决策时才唤醒**；其余（进度、阈值上报、常规回报）走静默投递，主会话下次醒来顺带看到。
- 与 §1.6 是同一套机制。

---

## 7. 第 8 点：截图规范

用户实测发现的视觉问题（团队没发现）：传送门离远看是**黑洞虚空**、贴近看画面**被放大失真**。

**要求**：
- 分辨率 **1920x1080**，不能是缩略图。
- **多角度、多距离**：走近、退后、侧面、俯仰都要看。
- **每个地方都要截**，逐处检查视觉问题。
- **站在玩家视角**判断好不好看，不是「能渲染就行」。

---

## 8. 第 9 点：玩家式测试

用户实测发现团队没发现的问题：**地上的传送门走进去会卡进地下虚空，没有传送**。

**要求**：像真玩家一样试，而不是只跑断言：
- UI 点击、菜单、按钮的真实操作。
- **各种鼠标移动方式**、**各种走路方式**（前后左右、斜向、贴墙、跳跃）。
- 专门验证**方向反了**这类 bug（左右移动反、鼠标上下反）。
- 验证**边界情况**：地面上的门、墙上的门、不同高度、不同角度进入。

## 9. 第 10 点：UI 显示全部代理的 token 消耗

（用户本轮未重申，但属于已提需求，列出待确认）

聊天栏底部现有两个消耗显示（只统计**主会话**）。在右边再加两个，显示**所有代理 + 主会话**的合计。
