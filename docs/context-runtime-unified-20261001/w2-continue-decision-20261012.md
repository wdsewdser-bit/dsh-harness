# W2 切窗是否值得继续投入

日期：2026-10-12。作者：Claude。方法：只读，依据仓库已有记录，没有新跑实验、没有发模型请求。
凡是我推算而非实测的数字，都标了“推算”。

## 结论

**继续保留 W2，但把它的定位从“省钱”改成“在必须缩上下文时不丢原文”。按这个定位，W2 现有的功能已经够用，不再给它加新能力；下一笔投入应该花在一次对照实验上，而不是花在机制上。**

具体是三条：

1. 停止为“字节更少”继续改 W2：不做规则 T（折队友原文）、不做权威进一步瘦身、不打开 E5 经济策略的 auto、不扩大名单。
2. 保持现状运行：生产名单模式 1 个会话，`minReductionRatio` 25% 门槛保留。
3. 做一次同任务三方对照（不折、摘要压缩、W2 多段折叠），外加在普通单代理会话上试“小交接 + 按编号取回”的形状。这一步要发真实模型请求，需要你点头。

## 证据：三次实测，结论并不都是负面

| 时间 | 对象 | 结果 | 出处 |
|---|---|---|---|
| 10-08 第一次 | 真实大 Team 根，此前已被摘要压缩两次 | 提交成功，请求从约 667KB 变成约 687KB，变大 | `execution-ledger.md` “检查点（10-08 约 00:00）” |
| 10-08 第二次 | 未压缩过的大根，384 条消息全在一个回合里 | 整回合折叠找不到区间；步区间只折到 2 条，2.23MB 变 2.59MB，被净收益门槛拒绝 | 同上 “恢复停点（10-08 约 04:00）” |
| 10-11 | 同一个根的隔离副本，多段 + 规则 R | 37 个不相邻区间一次提交，模型正文 2,158,609 B 变 1,362,998 B，减少 36.86%；80 条原文证人冷恢复后 SHA 全部一致；真实后继回合答对了任务约束 | `window-multi-acceptance-20261011.md` 第 22–26 行 |

所以“切窗后请求反而变大”是 10-08 的事实，不是最新事实。10-11 的多段折叠在同一个根上确实缩了三分之一。
外部评审核对文档和我昨天写的 `CURRENT_STATE.md` 第 3 节都只引了 10-08，没有引 10-11，这是遗漏，本次已改。

10-11 的数字有三个限制，验收报告自己也写了：它是模型正文 JSON 的字节数，不是线上字节、token 或费用；只有一个样本；是隔离副本，原生产根没有折过。

## 为什么缩了三分之一仍然不等于省钱

10-11 那次真实后继请求的用量是：input 443,586，cacheRead 1,408（`window-multi-acceptance-20261011.md` 第 25 行）。也就是折叠之后第一个请求几乎完全没有命中缓存。这是必然的：折叠改写了对话前缀，前缀缓存整段失效。

生产配置里记录的缓存未命中与命中价格比是 50（`home/profiles/web/cordis.patch.yml` 的 `cacheWriteReadRatio: 50`）。据此推算回本点：

- 设折叠前每个请求 T 个 token、全部命中；折叠后是 0.63T。
- 折叠后第一个请求按未命中计价，多付约 0.63T × 50 − T ≈ 30.5T 个“命中价单位”。
- 之后每个请求省 0.37T。
- 回本需要约 30.5 / 0.37 ≈ **83 个后续请求**，而且这 83 个请求之间缓存不能再失效（推算；假设 token 数与字节数同比例，且不折叠时缓存一直是热的）。

这个推算说明的是方向，不是精确值：**在缓存是热的时候主动折叠，几乎一定亏。** 你之前定的原则（75% 是硬上限、20 万 token 以下不折）和这个结论一致。

折叠只在一种情况下不亏：上下文无论如何都要缩，缓存无论如何都要失效一次。这时的对手不是“不折”，而是摘要压缩。

## W2 对摘要压缩：各自赢在哪

| | 摘要压缩 | W2 多段折叠 |
|---|---|---|
| 缩减幅度 | 大（整段换成一份摘要） | 10-11 实测约 37% |
| 之后每个请求的成本 | 更低 | 更高 |
| 原文 | 被摘要替代 | 人的输入、队友原文、最终回答逐字保留，其余可取回 |
| 缓存失效 | 一次 | 一次 |
| 实现与维护成本 | 原生已有 | 17 个 `team-v15-window-*` 插件文件，加原生多区间、计量器、压力缓存等消费面补丁 |

单看费用，摘要压缩更便宜。W2 能赢的只有保真度。所以 W2 值不值，取决于一个还没有被量过的问题：**摘要压缩在真实长任务上到底丢了多少要紧的东西。**

仓库里唯一的压缩质量对照是 `native-compaction-quality-AB-20261004.md`：三次真实摘要之后，模型仍然保住了计划路径、禁令和最新的范围修正。那次是带标签的人造历史、单根、一对样本，报告自己说不能当作稳定结论。也就是说，目前的证据是“压缩在小样本上没出事”，而没有“压缩出过事所以需要 W2”的直接记录。W2 的立项理由在数据上是空的。

## 我不同意的两个方向

- **不建议现在砍掉 W2。** 机制已经在真实大根上走通，冷恢复和原文一致性有证据，保持名单模式的持有成本很低。砍掉它等于放弃唯一一条“缩上下文但不丢原文”的已验证路径，而理由只是它不省钱，这个理由本来就不该是它的目标。
- **不建议继续做规则 T 和权威瘦身。** 这两项都是为了再多缩一些字节。但上面的算账说明，缩 37% 还是 50%，都改变不了“热缓存下折叠必亏、冷缓存下费用输给压缩”的格局。astra 也认为直接折队友原文不宜启用。在对照实验给出理由之前，这是在优化一个不决定成败的量。

## 建议的对照实验

目的是回答“摘要压缩丢的东西值不值得用 W2 的额外成本去保”，而不是再证明一次 W2 能跑。

1. 同一个任务、同一段前缀，分三组：不折、摘要压缩、W2 多段 + R。astra 在 `consult-window-economics-20261008-answer.md` 第 5 点提的就是这个设计。
2. 每组量四样：缩减后的请求 token、之后 N 个请求的 input 与 cacheRead、是否违反了早期约束、是否需要回头取原文以及取回是否成功。
3. 任务要故意放几条“早期说过、后面才用得上”的约束，否则三组都会通过，实验没有区分力。
4. 另开第四组，只在普通单代理会话上做：小绑定头 + 非权威工作摘要 + 按编号取回（核对文档末节讨论的形状）。它如果成立，缩减幅度接近摘要压缩，同时原文可取回，会同时压过压缩和 W2。它依赖模型自觉去取，DS v4.1-flash 能不能做到只能实测。Team 的租约、任务、冻结状态不交给模型，仍留在宿主。

预算沿用交接文档的保守上限：每组首批 16 个请求、input 100 万、并发 1。四组合计约 64 个请求。

判定规则事先写死：

- 压缩组没有丢约束：W2 维持名单模式，不再投入，长期看可以退役。
- 压缩组丢了约束而 W2 组没丢：W2 的定位成立，下一步是把它接成“到硬上限时替代压缩”的自动路径，而不是经济策略。
- 第四组不丢约束且缩减明显更大：普通会话走第四组的形状，W2 只留给 Team 根。

## 这份结论的局限

- 回本点是推算。缓存是否一直是热的、token 与字节是否同比例，都没有实测。
- 我没有读 `consult-fold-design-20261007-answer.md` 和 `consult-step-spans-20261008-answer.md` 全文，只读了台账里对它们的转述。
- 摘要压缩的缩减幅度写的是“大”，没有引用具体数字，因为仓库里没有和 10-11 同一个根的压缩对照。这正是建议做实验的原因。
