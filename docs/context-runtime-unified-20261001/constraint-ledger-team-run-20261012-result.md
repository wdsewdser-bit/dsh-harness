# 约束清单大型团队实测：结果（2026-10-12）

方案和判定规则见 [constraint-ledger-team-run-20261012-protocol.md](constraint-ledger-team-run-20261012-protocol.md)，在看到任何结果之前提交（b71db586）。本页按那份规则判定，没有事后改规则。

## 结论

1. **保留机制正常。** 5 个在压缩后继续工作的会话，压缩后的 264 个对话请求全部带着清单块，块的位置正确，条目一条不缺。
2. **按预登记的规则，这次触发了一条“有害”条款，只发生了一次。** 组长（lead）的清单在 14 条有效条目时撞到 4096 字节上限，最后一条新规则被 `CONSTRAINT_LEDGER_FULL` 拒绝，没有记进去。原因是上限按字节算而条目主要是中文。这是插件自己的缺陷，部署前要改（见“要改的地方”第 1 条）。
3. **摘要收集的噪声在线内。** 摘要小节收来的 34 条里，不是规则的误收为 0，重复 2 条。按最严的算法（把任务级规则和系统提示里已有的规则也算作噪声）是 8/34 = 24%，超过 20% 的线；按方案里“误收”的原意是 0%。两种算法都列在下面，我的判断是不需要关掉摘要收集，但要加一条机械去重。
4. **机械可判的违规为 0。** 没有对照组，这只说明清单没有妨碍，不说明是清单的功劳。
5. 实测顺带暴露了三个**与清单插件无关**的既有问题，其中两个比清单本身更值得先处理：压缩请求几乎整段不命中缓存；Team 成员压缩后被上下文安全检查永久拒绝。

## M4 噪声

| 类别 | 条数 | 说明 |
|---|---|---|
| 有效的新规则 | 26 | 六条用户裁定（三个会话各收回 5–6 条），加上成员自己撞到的不可用项 |
| 重复 | 2 | 同一会话里“不做移动端”分别以禁止项和不修项各列了一次；“无浏览器自动化”同理 |
| 任务级规则 | 5 | 成员的写入范围、被冻结不许改的文件。是真规则，但只对当前任务有效 |
| 系统提示里已有 | 1 | “没有获批的计划和租约不得写产品文件”，角色文件里本来就有 |
| 不是规则的误收 | 0 | |

另外有 3 条重复是在组长 04b5b2b8 的会话里收进来的，摘要器自己在条目后面写了 `(already recorded)`，之后模型自己调用工具把它们撤销了。

判定：按方案的原意（误收 = 把不是规则的东西收进来）是 0/34。把重复、任务级、系统提示已有的都算成噪声是 8/34 = 24%。我不认为这构成“噪声过大”：任务级规则在任务期间确实应该被遵守，问题只是它们在任务结束后不会自动失效。

更重要的一点是这 34 条的价值：这三个组员压缩前各自只用工具记了 1–2 条，用户的六条裁定全靠摘要小节收回。如果按“噪声过大”的处置关掉摘要收集，这些会话压缩后清单里就没有用户裁定。

## 顺带发现的三个既有问题

### 发现 A：压缩请求几乎整段不命中缓存

逐条消息比对压缩请求和它前一条对话请求（`driver/team-compaction-prefix.mjs`）：10 次里 8 次在第 6–8 条消息就分叉。分叉点都是同一种情况：对话请求里的大工具结果已经被既有的投影替换成约 2KB 的占位（`[large tool result replaced after its first 2 provider requests]`），而压缩请求发的是 21KB 的原文。

根因和我在实现清单插件时碰到的一样：投影层不处理压缩请求。于是每次压缩都要把几十万 token 当作全新输入付一遍。

修法是让投影层识别压缩请求并做同样的替换。这有一个代价要先想清楚：替换之后摘要器就看不到那些大工具结果的原文，只能看到占位。所以它不是纯省钱，会改变摘要的输入。这属于生产核心路径的改动，没有用户确认我不动。

量级：这次 10 个压缩请求未命中 339 万 token，如果前缀能命中，其中大部分会变成命中价。

### 发现 B：摘要器不可靠地遵守“不要重复”

指令里写了不要重列已有条目，摘要器仍然会把已有条目换一种语言或换个类别再列一遍，有时还自己标注 `(already recorded)`。现有去重只挡得住字面相同（忽略标点和大小写）的行。

修法：指令里要求对疑似重复的行写固定后缀 `(same as N)`，插件见到这个后缀就机械丢弃。摘要器已经自发在做类似标注，把格式固定下来即可。

### 发现 C：成员压缩后被上下文安全检查永久拒绝

`home/team-control-plane/pre-step-rejects.jsonl` 里有 27 条拒绝，全部来自 `team-v12-runtime`，原因 `team-context-safety-debt: required identity or task contract was omitted`：

- 审查员（verifier）10:12 压缩，之后连续 17 个回合被拒，直到宿主停止都没有再发出一个请求。
- integration 组长 11:06 第二次压缩，之后连续 10 个回合被拒。

被拒的回合没有模型调用，成员自己看不到原因。总组长的表现是反复重发消息、发现投递死信，最后另起了一个审查员。团队后半程的验收卡在这里，最终验收没走完和它直接相关。

代码里对应的位置是组装上下文包时必需项（多张任务卡的验收合同）装不进字节上限就 fail-closed。清单插件不挂这个钩子，块也只有几 KB，和它无关。这一项我只记录现象和位置，没有进一步定因，也没有改。

## 要改的地方（清单插件自己的）

1. **上限改成不会被中文挤爆的算法。** 候选：按字符算而不是字节；或把总上限提高到约 12KB（40 条 × 300 字符的量级）。我倾向按字符算并保留 40 条的条数上限，这样中英文行为一致。另外可以考虑给“用户裁定”留保底额度，让工具坑类的条目不能把它们挤出去；这次总组长的 14 条里多数是 Team 工具的坑。
2. **写满时的返回要告诉模型怎么办。** 现在只返回错误码。应附上当前有效条目和“先撤销一条再加”的提示。
3. **`(same as N)` 机械去重**，见发现 B。
4. **任务级规则的失效。** 现在只能靠模型自己撤销。可以先不做，观察真实使用里是否积压。

## 这次实测没回答的

- 没有对照组，不能归因。
- 摘要收来的条目在后续请求里的表现没有覆盖到（那 3 个会话压缩后就结束了）。
- 带块的压缩请求只有 1 个，带块对压缩缓存的影响没有数据。
- 没有任何会话发生第三次压缩，清单跨多次压缩的累积没有测到。
- 游戏本身没有在浏览器里验证。
