## 系统背景

DSH 是一个多智能体编码运行时：一个 Team 有根会话（tier 0，负责拆分与验收）、若干负责人和成员，每个都是独立的长会话，模型窗口约 100 万 token。运行时已有两套“折叠上下文”的机制：

**1. 压缩（compaction，已在生产使用）**
- 把较早的对话替换成一段由模型生成的固定八段结构摘要；原始日志仍在磁盘上，但摘要之后模型看不到原文。
- 触发：(a) 模型在“一个大阶段完成”时主动打里程碑勾，随后空闲时折叠；上下文低于 20 万 token 时即使打勾也不折（缓存还热、注意力最好，折了不划算）；(b) 硬上限：到窗口的 75% 时引擎在下一步开始前强制压缩。
- 压完后运行时会重发身份与任务合同的基线，并做“锚点校验 + 恢复通知”。
- 已知问题：一次压缩要把被折叠的全部内容连同输出上限一起发给模型；真实任务里有成员在不空闲的长回合中涨到 87 万 token，这时压缩请求本身被服务商拒绝（输入 + 输出上限超窗），该成员就此无法继续。

**2. 持久切窗（W2，已实现并通过实验，生产中没有调用方）**
- 把较早的一段 surface 替换为一条“历史检查点”消息，内容是：权威状态快照（看板任务、计划、需求、身份、租约）+ 原文事件的引用。**不含对话内容的摘要。** 之后每个请求会附带一条“当前权威状态”消息。
- 原文按回合保留副本，可精确取回。
- 提交过程是带持久意图（intent）的两阶段写入，提交点对身份/计划/配置/宿主状态做 CAS 核对，冲突则写 ABORTED 并让路，崩溃后可恢复。
- 准入条件：必须是 Team 根会话，且控制面里有一份“已登记的计划合同”（由 `plan_register` 从磁盘上的 JSON 合同文件登记：planId、scope、items[requirementId, taskRefs…]）。

## 刚发现的问题

核对三个真实 Team（一个 6 小时、42 个会话、145 个任务的任务；一个 40 分钟的小任务；用户自己的长期项目）的控制面：**已登记计划数都是 0**。真实 Team 用的是另一套按任务提出并批准的计划（每个任务一条：requirementId、goal、members、writeScopes、checks、approvedBy…），角色提示词里也从未要求登记计划合同。所以按现设计，切窗在真实使用中一次都不会触发；依赖同一份登记计划的“最终交付门”也从未真正生效。

## 已有的真实数据

- 价格（每百万 token）：未命中缓存的输入 0.15 美元，命中 0.003 美元，输出 0.60 美元。缓存按消息前缀对齐，改写靠前的消息会让其后全部失效。请求间隔在 15 分钟内缓存命中率中位数约 99%，超过 60 分钟降到约 3%。
- 30–60k 上下文时折叠没有质量收益且更贵；100k/300k/500k 时压缩与不压缩两臂都答对，压缩的成本劣势随上下文增大而缩小。
- 单次请求内的查找、多跳推理到 90 万 token 基本不衰减；需要“把全文数一遍”的任务从 50 万起开始出错。
- 6 小时的真实任务：45 次压缩，全部发生在 20 万以上；7 个会话超过 50 万，6 个到过 78.6 万以上；一个成员因上述原因报废。
- 折一次 42 万 token 的上下文，摘要调用成本约几美分——切窗相对压缩的成本优势不大。
- 用户习惯边工作边热重载插件；重载时进行中的切窗会中止并可重试。

## 正在讨论的三个方向

**A+B 融合**：计划合同的内容由宿主从已批准的任务计划自动派生并登记（不依赖模型）；计划“版本”只在阶段边界发布——模型打里程碑勾时，或宿主准备切窗前若有未发布变更则自动发布一次。这样版本变化的节奏与折叠节奏对齐，日常的任务变更不会打断切窗的 CAS 核对。

**C（统一折叠）**：不再把“切窗”和“压缩”当成两种机制，而是一种折叠，由四部分组成：
- 摘要（对话要点，来自模型；可选，权威状态覆盖充分时可以很短或省略）；
- 权威状态快照（看板/计划/身份，有什么带什么，各域可选并显式声明覆盖范围）；
- 原文可精确取回；
- 持久意图 + 提交时 CAS + 崩溃恢复。
普通会话 = 摘要 + 原文可取回；Team 根 = 短摘要 + 完整权威状态。上下文大到摘要请求发不出去时，可退化为“不生成摘要、只保留权威状态和原文引用”把会话救回来。代价是重新设计检查点格式、采集器和恢复流程。

**分两步**：先做 A+B 让切窗在 Team 根上跑起来拿数据，再决定是否做 C。

## 请你回答

1. A+B 融合是否合理？“版本只在阶段边界发布 + 切窗前自动发布”有没有会导致权威状态与计划不一致、或 CAS 形同虚设的漏洞？自动派生的计划合同应该包含什么、不应该包含什么？

3. 在这些数据下（缓存定价、20 万下限、75% 硬上限、长回合不空闲会越过硬上限），你会怎样设计触发策略与机制选择？特别是：如何保证硬上限真正兜得住；摘要请求发不出去时的退路；折叠后缓存前缀怎样安排才能尽快回到高命中。
4. 有没有比这三个方向更好的方案，或者这套设计里你认为根本不该做、可以删掉的部分？
5. 如果由你来排优先级，接下来的三件事是什么，各自的验收标准是什么？
