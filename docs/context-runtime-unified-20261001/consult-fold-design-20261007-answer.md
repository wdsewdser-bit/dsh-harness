**1．A+B 合理，但阶段发布不能代替实时一致性，也不能证明需求完整性。**

建议明确区分三个版本：

| 版本 | 何时变化 | 作用 |
|---|---|---|
| 已批准计划来源版本 | 批准、撤销、范围或验收要求变化时立即更新 | 表示当前实际承诺 |
| 已发布计划合同版本 | 初次建立、阶段边界、切窗前、最终交付前发布 | 提供稳定、可引用的合同 |
| 实时权威状态版本 | 任务、身份、租约、输入等相关事实变化时更新 | 决定当前能做什么，并参与 CAS |

**可以推迟发布合同，不能推迟权限撤销、范围收缩或新用户约束的生效。** 历史合同只说明某个版本的承诺，不能继续授予已经失效的权限。

安全的发布与切窗顺序应当是：

1. 从一致的控制面快照确定性派生合同；内容未变就不增加合同版本。
2. 发布时核对派生依据仍有效，保存来源版本、哈希及批准凭据。
3. 重新采集检查点；发现尚未发布的合同语义变更就重新准备。
4. 提交时校验实际权威状态、合同、身份、租约、surface、配置和输入边界；冲突就中止，不能只刷新 expected 值继续提交。

“切窗前自动发布”应当是准备工作的前置步骤，不能在已有 PREPARED intent 中悄悄替换合同。

而且，**B 对现有 CAS 冲突的改善不能高估**：collector 目前绑定了 `controlRevision`、`authorityHash` 和 `planHash`，transition 仍持有控制面围栏跨过落盘。因此，减少计划版本变化并不会自动消除任务状态变化带来的等待或冲突。[collector](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/team-v15-window-collector.mjs:239)、[transition](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/team-v15-window-transition.mjs:109)

建议先保留这些校验。以后若要缩小冲突范围，应按实际读到的相关域建立版本向量，并验证没有漏掉写入者；不能以“降低冲突”为理由冻结实时版本。

自动派生合同应该包含：

- 稳定的需求 ID、任务映射、目标、范围、验收要求、条件项和明确排除项。
- 被批准的任务计划版本及其来源、批准凭据。
- 合同覆盖范围，例如“覆盖全部已批准任务计划”，以及尚未映射的需求。
- 派生规则版本、来源版本和内容哈希。

不应包含不断变化的任务进度、心跳、当前租约有效性、运行中作业状态，以及“已通过”“已交付”等结论。这些属于实时状态和证据。合同规定需要什么证明，证据系统判断证明是否成立。

这里最大的风险其实是最终交付门：**从已批准任务反推出来的集合，只能证明这些任务的覆盖，不能发现根本没建成任务的需求。** 仓库规范对此已有明确要求：“把计划条目映射到任务，而非以目前任务列表反推出计划范围”。[实施计划 §4.2](D:/dsh-test/docs/context-runtime-unified-20261001/implementation-plan.md:141)

因此我建议：

- 切窗可以接受“已批准任务计划投影”，但必须声明覆盖有限。
- 整体交付必须另有用户需求范围的来源及完整性核对。
- 缺少完整需求清单时，整体完成状态应为“覆盖未知”，不能自动通过。
- 最终交付前也要发布未发布变更，不能只在里程碑和切窗前发布。

现有 `normalizePlan` 还要求每个需求至少绑定一个任务。改造时必须能表达“需求存在但尚未建任务”，或单独核对这些缺口，不能为了通过 schema 把它们过滤掉。[代码](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/team-v15-plan-delivery.mjs:35)

**2．C 的方向正确；无摘要切窗可以使用，但不能默认认为精确取回足以维持工作。**

原文保留解决数据完整性；摘要或工作备忘解决“当前在做什么、哪些信息值得找、为什么作出这个决定”。精确检索的弱点是：模型可能不知道自己遗漏了什么。

成员尤其容易丢失未写入任务计划的内容：失败假设、选型理由、临时发现、尚未验证的风险。根会话也存在这些信息，所以“权威状态完整”不自动意味着“对话语义已经覆盖”。

我的默认策略是：

- 普通会话、成员：保留简短工作摘要、近期原文和精确恢复入口。
- Team 根：宿主生成权威状态，摘要只记录其中没有表达的决策理由、未决问题和下一步。
- 无摘要：用于经过验证的充分结构化场景，以及应急恢复；恢复后可以先取回资料，再继续执行。

四部分建议这样定：

| 部分 | 要求 |
|---|---|
| 模型摘要 | 可选。可以由仍然有效的工作备忘和近期原文替代；缺少续接信息时显式进入恢复阶段。 |
| 权威状态 | 各业务域按适用性提供；覆盖声明、来源及版本必须有。区分“不适用”“已覆盖”“不可用”，不能把缺失解释为空。 |
| 原文精确取回 | 持久折叠必须具备，包括可调用入口、定位信息、权限与保留保证；仅保留文件路径不够。 |
| 持久提交与恢复 | 必须具备。当前跨域结构保留 intent、CAS、持久化屏障和幂等恢复；若未来有真正的原子事务，可由事务提供等价保证。 |

此外，四部分之外还应明确一个强制不变量：**工具协议完整、未完成副作用可对账、待处理输入不丢失。**

当前 W2 有一个必须正视的限制：它只选择已完成回合，并保护当前回合；安装时使用的也是 `whole-completed-turn-v1`。[collector](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/team-v15-window-collector.mjs:198)、[install](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/team-v15-window-install.mjs:157)

因此，直接把现有 W2 扩展到成员，并不能救正在膨胀的单个长回合。应急路径需要支持**回合内部、工具调用已经结算且协议允许切开的步边界**。若供应商协议要求保留的不可拆片段本身已经超窗，就只能暂停并恢复，不能保证自动续跑。

**3．触发策略应以安全预算为硬约束，以阶段完成为主要折叠机会。**

我会保留 20 万下限和 75% 压力阈值，但调整它们的含义：

| 场景 | 推荐行为 |
|---|---|
| 低于 20 万，预算安全 | 不做经济性折叠；里程碑只记录。 |
| 超过 20 万，大阶段刚结束 | 主要折叠机会，保留正常摘要路径。 |
| 超过 20 万，缓存可能已冷 | 可以择机折叠；不能仅凭间隔或上次低命中强制折叠。 |
| 达到 50 万，阶段未结束 | 加强预算预警，不设无条件必折规则。 |
| 达到 75%，或下一请求预算不安全 | 暂停正常采样，先缩减或恢复，不等待整个回合空闲。 |

50 万时穷举计数出错，支持把这类任务交给确定性程序计数；它不足以证明所有编码任务都应在 50 万折叠。单次长上下文答对，也不能证明多轮反复折叠没有损失。

按你提供的价格，假设从 50 万折到 10 万、摘要费用 0.03 美元，热缓存下每次后续请求少花约 0.0012 美元；加上约 0.0147 美元的重建缓存差额，粗算约 **38 次后续请求**才回本，尚未计算额外取回成本。因此，成本不支持频繁主动折叠。

真正的硬兜底应放在**最终请求发送前**，并覆盖正常请求、摘要请求和其他模型调用：

```text
最终输入 token + 本次输出预留 + 安全余量 ≤ 当前路由模型窗口
摘要输入 token + 摘要输出预留 + 安全余量 ≤ 摘要模型窗口
```

这里的输入必须包含最后注入的身份、工具 schema、权威状态、待处理输入和工具结果，不能只看旧 surface 的计数。75% 是启动处理的阈值，上面两个条件才是发送准入条件。

现有引擎已经在 `agent/pre-step` 尝试压缩，但失败后会打印 `continuing the turn` 并继续；插件预算检查又是单独可关闭的入口。因此，不能把“配置了 0.75”当成已经具备硬保证。[压缩引擎](D:/dsh-test/staging/context-runtime-unified-20261001/app/node_modules/@deepseek-ai/dsh-compaction-basic/lib/index.js:859)、[预算检查](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/step-compaction-v4.mjs:374)

还需要限制单步增长：大工具结果完整落盘，进入模型请求的内容有预算，并提供精确取回入口。否则一次工具返回就可能跨越全部预留空间。

摘要发不出去时，我建议固定采用以下退路：

1. **先尝试有界局部摘要。** 只选能够装入摘要请求的较早连续片段，保持协议完整；不要求一次总结全部待折叠历史。摘要输出预算独立配置。
2. **仍无法摘要时，提交无摘要恢复检查点。** 保留目标与约束、可得的权威状态、近期完整协议片段、原文索引，并明确哪些信息尚待取回。先恢复必要信息，再执行依赖它的修改或验收。
3. **没有可安全切开的片段，或恢复来源不可用时，进入可恢复暂停。** 不反复发送同一个超窗包，也不删除尚未对账的内容。

本地“绝不发送已知超预算请求”可以作为验收目标；服务商真实计数未知时，不能承诺永远不被拒绝，需要保守估算、余量和拒绝后的有界恢复。

缓存方面，建议请求顺序保持为：

```text
稳定系统/工具契约 → 本窗口固定检查点 → 持续追加的历史 → 当前动态状态
```

检查点在本窗口内不反复改写；动态消息尽量靠后；内容未变时保持序列化稳定，避免无意义时间戳、随机字段和排序变化。当前 surface 把 current-authority 放在末尾，这个方向应保留。[代码](D:/dsh-test/staging/context-runtime-unified-20261001/home/profiles/web/plugins/team-v15-window-surface.mjs:110)

同时设置折叠后的冷却与最小新增量，避免因为折后第一次低命中再次折叠。现有 decision 已识别这个问题，值得保留。缓存实际命中仍需以 usage 验证；官方说明缓存前缀必须先持久化，且不保证每次命中，所以不能承诺折后第二次就恢复到 99%。[DeepSeek 缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

**4．更好的落地方式是“统一底层保证，保留不同内容策略”。**

这相当于收敛后的 C：

- 共用请求预算、片段选择、原文恢复、提交和崩溃恢复。
- 摘要生成和权威状态采集是可组合模块。
- A+B 负责适配现有批准流程，不负责决定所有会话是否有资格折叠。
- 普通会话无需伪造 Team 计划、看板或租约。

我会取消“完整登记计划是所有持久折叠的必要条件”，但保留它在**整体交付完整性**中的作用。两者需要的证明不同。

不建议继续投入的部分包括：把 W1 当常规裁剪器、把固定八段格式当底层事务契约，以及仅靠提高回合副本数量上限解决长期增长。八段摘要可以继续作为模板；原文保留则应逐步采用分段索引和明确的保留策略。现有检查点已经有 `working`、`recovery` 等位置，没必要先做一次全面重写。

**5．接下来的三件事及验收标准。**

| 优先级 | 工作 | 验收标准 |
|---|---|---|
| **第一：修复预算与超窗恢复** | 最终发送前检查两类预算；有界局部摘要；明确恢复或暂停路径。 | 根、成员、普通会话都覆盖：长回合不空闲、大工具返回、末尾注入、摘要超窗及摘要不可用。已知超预算请求零发送；恢复过程中原文、待处理输入和副作用回执不丢；安全可切片案例能够继续工作，无法切片案例明确暂停，不能死循环重试。 |
| **第二：打通修正版 A+B，并分开任务覆盖与需求完整性** | 确定性派生、稳定发布、来源追踪；最终交付前刷新合同。 | 未手动 `plan_register` 的真实形态 Team 能自动生成任务投影；相同内容不增版本。“十项需求只建六项任务”、新增约束未发布、撤销批准都不能通过整体交付。提交期间改变关键来源必须中止旧检查点；普通状态变化不会无意义重发合同。 |

上述第三步是否应默认省略摘要，目前证据不足；我的默认值仍是**短摘要加权威状态**。真正值得优先统一的是预算、提交和恢复保证。
