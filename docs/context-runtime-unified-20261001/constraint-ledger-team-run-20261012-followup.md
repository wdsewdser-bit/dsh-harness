## 1. 清单上限

`constraint-ledger.mjs`（web 和 headless 两份相同）：

- `activeBytes: 4096` 改为 `activeChars: 8000`，按字符串长度算。条数上限 40 不变。实测里组长的 14 条约 3.3KB 字节、约 1500 字符，新上限下 40 条的条数限制会先生效。
- 写满时 `constraint_note` 的返回除了错误码，还带当前全部有效条目和一句提示：先撤销一条过时或可合并的，再重新添加。仍然是拒绝，不自动淘汰。
- 压缩指令里加一条规则：不确定某行是否重复时可以列，但行尾必须写 `(same as N)`。解析摘要时，行尾带 `(same as N)` 或 `(already recorded)` 的行直接丢弃，不进清单。后一种写法是实测里摘要器自己发明的。

没有做的：给“用户裁定”留保底额度。条目没有可靠的办法区分是不是用户裁定，先看新上限下是否还会写满。

## 2. 压缩请求的缓存

根因（实测时已确认）：投影层要求每条消息都有 id，原生压缩请求末尾那条指令没有 id，整个请求被判为“不认识”而跳过全部变换。于是对话请求里大工具结果已经换成占位，压缩请求发的却是原文，从第 6–8 条消息起就对不上。

`request-message-projection.mjs`（web 和 headless 两份相同）：

- 识别“用途是压缩、只有最后一条是没有 id 的用户指令、去掉它之后其余消息都合规”这一种形态。其他任何不认识的形态仍然整条跳过。
- 对这种请求只投影历史部分，末尾指令原样接回，不传给任何变换。
- 只运行各变换的纯函数版本，不触发发送后的回调。这样大工具结果的“已发送次数”之类的内部计数不会因为一次压缩而变化。
- 投影历史时把用途报告为对话。原因是有的变换对非对话请求直接不处理，那样历史仍会和对话请求不同。最终发出的请求用途不变。
- 结果不冻结，因为清单插件随后要在指令末尾追加小节。

这改变了一件事，需要明确：**摘要器现在看到的历史和模型自己看到的一样**，被替换成占位的大工具结果它也只能看到占位。我认为这是合理的，模型在这些结果被替换之后本来也看不到原文；但如果以后发现摘要质量因此下降，这里是第一个要看的地方。

隔离副本 `output/team-run-followup-20261012/v1`，生产插件集上覆盖 staging 的四个文件。一个会话：依次读三个约 30KB 的文件、几次查询、手动压缩、再读再查、再压缩。23 个请求，12:33–12:38 UTC。

|---|---|---|---|
| 第 1 次压缩 | 992 | 51,200 | 19 条 / 19 条，27,166 字节全部相同 |
| 第 2 次压缩 | 909 | 50,688 | 17 条 / 17 条，26,508 字节全部相同 |

压缩请求和它前一条对话请求只差末尾那条指令。请求里有 16 处大工具结果占位，说明替换确实发生了并且两边一致。两次压缩请求都带上了清单的追加小节，第二次带着清单块；压缩后的 8 个对话请求都带完整清单块；最后一问模型能列出清单里的约束。

## 3. 压缩后被永久拒绝

根因：压缩之后，运行时要把成员的身份、名下任务、范围内的需求和裁定、房间摘要等“必需来源”一次性重新交付，总量不得超过上下文包上限（实测配置 32000 token）。只要有一条必需来源装不下，这一步就被拒绝。被拒的成员一步都执行不了，也就没法按提示去取回缺的内容，于是每个回合都被拒，直到宿主停止。任务和需求越积越多，范围大的成员（审查员、组长）迟早会撞上。

`team-v14-context-delivery.mjs` 和 `team-v12-runtime.mjs`（headless 已同步）：

- 来源可以带一个紧凑形态。全部必需来源用完整形态装不下时，从优先级最低的开始逐个改用紧凑形态，直到装下为止。
- 目前只给需求和裁定提供紧凑形态，内容就是总组长（tier 0）本来就在用的那种“摘要 + 取回指针”。身份和名下任务这类安全关键的来源不压缩。
- 压到底仍装不下，行为和以前一样（拒绝）。
- 没有触发回退时，输出和改动前逐字节相同，有测试钉住。

需要知道的代价：以紧凑形态交付的需求，之后不会自动补发完整内容。成员看到的是摘要，要完整的验收条目得自己按指针去取。这和总组长一直以来的情况相同。

**没有真实验证。** 复现它需要一个成员在压缩时名下范围超过 32000 token，这次实测花了约 45 分钟、上千个请求才出现。单测用构造的来源复现了“修之前拒绝、修之后通过”，但运行时里给来源挂紧凑形态的那几行没有被任何测试实际执行，只过了语法检查和全量回归。下一次跑大型团队时，看 `pre-step-rejects.jsonl` 是否还出现 `team-context-safety-debt`，以及日志里是否出现紧凑交付的记录。
