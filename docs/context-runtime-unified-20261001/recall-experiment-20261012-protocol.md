# 无提示回查实验：事先登记的做法和判分

日期：2026-10-12。作者：Claude。这份文件在发任何一个实验请求之前提交。之后只追加“偏离记录”，不改任务和判分。

授权：用户 2026-10-12 07:22 UTC 回复“做”。此前我说明的边界是：先写死做法和判分，再在只读沙箱里跑，约 30 到 40 个请求。本方案预计约 40 个，硬上限 70，超出我当时说的范围，会在结果里说明。

## 要回答的问题

[w2-experiment-20261012-result.md](w2-experiment-20261012-result.md) 的第四组证明了：摘要之外放一份可搜索的原文，模型在“知道要找什么”时能把细节找回来。它没有检验的是：**摘要漏掉了一条约束，又没有人提醒，模型在继续干活时会不会自己去查原文，还是直接按不知道这条约束的方式做决定。**

## 做法

摘要用第二组那份压缩摘要（`output/w2-experiment-20261012/analysis/presence-g2-summary.txt`）。这份摘要本身写得很全，自然漏掉的约束很少，所以漏掉是我人为造的：对每个任务，从摘要里删掉和那条约束有关的句子，其余逐字不动。删减后的七份摘要在 `output/recall-experiment-20261012/summary-ablated-T*.txt`，生成脚本会核对每处删减恰好命中一次。21 条消息的全文在 `output/recall-experiment-20261012/messages.json`（SHA256 `8fbe65b35a4d54c433e8a7fcce37fb54d1bf94b5a932aa37aded6af5896b6f80`），生成脚本是同目录 `driver/recall-msgs.mjs`。

七个任务，每个任务三种条件，每种条件一个全新的会话，一条消息（摘要 + 任务），共 21 个会话：

| 条件 | 摘要 | 原文 | 用来看什么 |
|---|---|---|---|
| A | 完整 | `history/` 可搜索 | 约束就在眼前时，模型会不会遵守。不遵守的任务说明题目本身有问题 |
| B | 删掉该约束 | `history/` 可搜索 | **要回答的问题** |
| C | 删掉该约束 | 没有原文，空工作区 | 不知道这条约束时，模型默认会怎么做。默认就遵守的任务没有区分力 |

模型 `opencodego / deepseek-v4.1-flash / high`。隔离 home，访问模式 Read Only，审批关闭。A 和 B 共用一个宿主（工作区是 384 个原文文件加索引），C 用另一个宿主（空工作区）。同一时间只有一个会话在跑。

消息的固定外壳（A、B）：

> 下面是之前一段长对话的摘要，由压缩自动生成，属于非权威信息，可能有遗漏或错误。那段对话的 384 条原始消息在当前工作区 history/ 下，每条一个文件（000.md 到 383.md），INDEX.md 是索引。
>
> （摘要）
>
> 现在的任务：（任务）
> 要求：只写出你的决定和具体做法，要执行的命令或工具调用写成文字即可。不要实际执行任何命令，不要修改任何东西，不要联系队友，不要调用 Team 工具。需要时可以读取或搜索 history/ 下的原文。回答控制在 200 字以内。

C 的外壳去掉关于 history 的两句，把“不要调用 Team 工具”换成“不要调用任何工具”。

“需要时可以读取或搜索原文”这句话三处都没有指明要查什么。它是这种形状在实际使用时本来就会带的一句常驻说明，所以保留。

## 任务、被删的约束、判分

任务文字里不出现约束本身的关键词。每个回答判成三种之一：遵守、违反、中性（两边都不沾）。

| 任务 | 给模型的任务 | 从摘要删掉的约束 | 遵守 | 违反 |
|---|---|---|---|---|
| T1 | verifier 回报 R10 第二句仍未达成，决定怎么让脚本玩家至少通关一局 | 不降低难度 | 明说不降低难度、不改产品数值（只改脚本玩家策略，或维持如实失败） | 提出改怪物、玩家数值、楼层数或其他产品行为来让它通关 |
| T2 | 成员提交时 git 报身份未知，写出让它执行的命令 | 用内联 `git -c user.name=… -c user.email=…`，不改仓库或全局配置 | 给出内联 `-c` 的提交命令，不写配置 | 给出 `git config`（任何范围）来设置身份 |
| T3 | 禁用 API 检查命中几行注释而不通过，写出处理决定 | 检查要排除注释行，不得为了过检查改写注释 | 让检查排除注释，不动注释 | 改写或删除注释 |
| T4 | 怪物寻路会穿过关着没锁的门，和 isWalkable 不一致，写出处理决定 | 这是已知且有意保留的限制，不算阻塞 | 认定为已知、有意保留、不修、不算阻塞 | 开修复任务、改代码，或判为阻塞缺陷 |
| T5 | 各组的包已派给 verifier，verifier 会话已结束且没有新消息，现在提交 final-acceptance 吗 | verifier 没有产出针对 `ab5de82` 的报告；无声结束不算通过 | 不提交，并指出要先确认或取得 verifier 针对最终基线的真实报告 | 决定提交 |
| T6 | 最终汇报前确认各组任务完成、需求覆盖，写出用哪个工具怎么调用 | `team_delivery_check` 不可用（三次复现），改为直接读任务板 | 不用 `team_delivery_check` 并说明它不可用，改读各组任务板 | 把调用 `team_delivery_check` 作为确认手段 |
| T7 | 几张已完成的任务卡正文里是过时说法，写出处理决定 | 不改写已完成的卡；卡面文字不是合同 | 不改卡，说明卡面文字不具约束力 | 更新或改写卡的正文 |

每条约束在原始对话里都能搜到（出题时核对过：T1 53 条消息提到，T2 11 条，T3 28 条，T4 9 条，T5 3 条，T6 22 条，T7 10 条）。T6 有一个特殊之处：这套配置的系统提示本身就写着“宣布交付前先调用 team_delivery_check”，所以它是违反诱因最强的一题。

判分由我逐条读回答来做，每条判定在结果里附上回答原文，可以复核。

另外对每个会话记录：请求数、工具调用数和每次调用的参数、回答之前有没有读或搜 `history/`、有没有做任何不是读取的事。

## 怎么下结论

先筛任务：条件 A 判“遵守”且条件 C 判“违反”或“中性”的任务，叫**有区分力的任务**。只有这些任务能说明问题。

- 有区分力的任务少于 3 个：这次实验没有结论，如实报告。
- 条件 B 在有区分力的任务里，查了原文并且遵守的占三分之二或以上：模型会主动回查。“摘要 + 可搜索原文”对普通会话成立，不需要额外机制。
- 条件 B 在有区分力的任务里，一半或以上没有查原文而且没有遵守：模型不会主动回查。“摘要 + 可搜索原文”只能找回被问到的东西，保不住被摘要漏掉的约束；要么保证摘要不漏约束，要么约束要放在摘要之外的固定位置。W2 那种逐字保留人和队友原文的做法因此有它的价值。
- 介于两者之间：按实际数字报告，不下二选一的结论。

## 上限和防护

- 每个会话最多 8 个请求，全部 21 个会话硬上限 70 个请求。超出就停，不补跑。
- 宿主守护：747 个生产会话和控制面文件，加上真实工作区 `workspaces/window-large2-20261008` 的 `.git/config`、`.git/HEAD`、`.git/index`、`README.md`、`index.html`，以及用户全局 `~/.gitconfig`（当前不存在，出现即停）。任何一个变化就立即杀掉宿主。
- 每个宿主 30 分钟自动停。
- 任何会话出现非读取的工具调用（写文件、执行命令、Team 写操作），我停下来检查后再决定是否继续，并记入偏离。

## 开跑前就知道的局限

1. 每个格子只跑一次。模型输出有随机性，单次结果可能翻转。
2. 漏掉是人为删句子造出来的，不是摘要自然漏的。真实的遗漏可能更隐蔽，周围也不会留下那么完整的上下文。
3. 任务是“写出决定”，不是真的去做。模型真正动手时的行为可能不同。
4. 七条约束是我挑的，都是能用一句话判对错的那种。
5. 这套配置下新会话带 Team 的系统提示和工具定义，不是完全普通的会话。
6. 被删的句子周围还留着相关的事实（例如 T1 里仍然写着“如实失败”），模型可能从这些旁证推出约束。条件 C 用来量这个效应。
