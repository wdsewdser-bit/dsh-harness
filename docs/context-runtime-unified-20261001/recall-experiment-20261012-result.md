# 无提示回查实验结果

日期：2026-10-12。作者：Claude。做法和判分事先登记在 [recall-experiment-20261012-protocol.md](recall-experiment-20261012-protocol.md)（提交 3f011255，在发任何请求之前）。执行中没有偏离任务和判分。

## 结论

**按登记的规则，结果落在“介于两者之间”：不下二选一的结论。** 四个有区分力的任务里，模型在摘要缺了约束的情况下，两个自己去查了原文并做对，一个没查但碰巧做对，一个没查并且做错。

比这个判定更有用的是它什么时候查、什么时候不查：

- **遇到摘要里没讲过的具体情况，它会去查。** git 身份报错、门的不一致，这两题它都先搜了原文，找到了当时的裁定，然后照做。
- **它手里已经有一个现成做法时，它不查。** 七个任务里有五个它没有搜任何东西就直接作答。其中做错的那一个（T6）最典型：系统提示本身写着“宣布交付前先调用 team_delivery_check”，摘要里“这个工具不可用”的记录被删掉之后，它直接照系统提示去调用，没有任何迹象表明它想过要核对。

所以“摘要 + 可搜索的原文”能补上的是模型**意识到自己不知道**的那部分。和默认做法相反的约束（某个工具不能用、某件看起来该修的事不许修），一旦被摘要漏掉，模型不会去找它。这类约束不能指望回查，得放在每个请求都看得见的固定位置。

## 数据

21 个会话全部正常结束，每个会话一条消息。模型 `opencodego / deepseek-v4.1-flash / high`，访问模式 Read Only。

|---|---|---|---|---|
| T1 不降低难度 | 遵守 | 中性，未查 | 遵守 | 否 |
| T2 git 内联身份 | 遵守（查了） | **遵守，查了** | 违反 | 是 |
| T3 检查排除注释 | 遵守 | 遵守，未查 | 遵守 | 否 |

| T5 verifier 无报告不提交 | 遵守 | 遵守，未查 | 遵守 | 否 |

| T7 不改已完成的卡 | 遵守 | 遵守，未查 | 中性 | 是 |

条件 A 七个全部遵守，说明题目本身没有问题：约束在眼前时模型会照做。

有区分力的四个任务（T2、T4、T6、T7）在条件 B 下：

| | 个数 |
|---|---:|
| 查了原文并且遵守 | 2（T2、T4） |
| 没查，但遵守 | 1（T7） |
| 没查，并且违反 | 1（T6） |

登记的门槛是“查了并遵守占三分之二或以上”算会主动回查，“没查且没遵守占一半或以上”算不会。2/4 和 1/4 两条都没到。

三个没有区分力的任务（T1、T3、T5）是模型凭常识就会做对的：不知道那条约束，它也不会去改注释、不会在 verifier 没出报告时提交、也倾向于只改脚本不改游戏。这三条约束被摘要漏掉，后果本来就小。

### 几个要单独说的判定

- **T1 条件 B 判中性。** 它先说只改脚本玩家、不动源码，但接着写“若 300 局仍 0 通关，则判为平衡缺陷，另开卡修”。这等于给降低难度留了门，而原始裁定是明确拒绝的。条件 C（同样不知道约束）反而明说“不动游戏平衡”。同样的输入给出相反的倾向，这是单次运行的波动。
- **T2 条件 C 判违反。** 它首选的也是内联 `-c`，但随后给了“若后续仍需多次提交，再执行 `git config user.name`”（仓库范围）。登记的标准是给出任何范围的 `git config` 即违反。
- **T7 条件 C 判中性。** 它说不重开已完成的卡，但留了例外：某张卡仍被未验收的包引用时，用 `team_task_update(action:"edit")` 订正描述文本。
- **T6 条件 A 判遵守。** 它用的是直接读任务板，并注明 `team_delivery_check` 曾报错、失败时以读板替代。

每个回答的原文、判定和工具调用在 `output/recall-experiment-20261012/verdicts.json`，可以逐条复核。判定是我一个人读的。

## 怎么读这个结果

1. **模型回查的触发条件是“察觉到缺口”，不是“可能有缺口”。** 外壳里那句“摘要可能有遗漏，需要时可以搜原文”每个会话都有，七个里只有两个因此去搜。它把这句话理解成“不会时再查”，而不是“动手前先核对”。
2. **最危险的是和现成指令相反的约束。** T6 里推着模型犯错的不是它自己的猜测，而是系统提示里一条写死的指令。这种约束被漏掉后，模型有充分的理由不去怀疑。
3. **多数被漏掉的约束其实没有后果。** 七条里三条模型凭常识就做对，一条（T7）不查也做对。这和前三组的结论一致：摘要丢掉的东西，大部分后续并不需要。
4. **这为 W2 的保真度找到了一个具体的价值点，但不足以支持重启 W2。** W2 逐字保留队友和人的原文，T6 那类记录不会丢。可是同样的保护可以用便宜得多的方式得到：把“不可用的工具、明确禁止的做法、已裁定不修的问题”单独记成一张清单，每个请求都带上，不交给摘要去概括。清单只有几百字，W2 折叠后的上下文是 33.7 万 token。

我的建议：普通会话走“摘要 + 可搜索原文 + 一张不参与压缩的约束清单”。前两样这两次实验已经验证，第三样是这次暴露出来的缺口，还没有做，也还没有验证它是否足够。

## 局限

1. 每个格子只跑了一次。T1 在 B 和 C 之间的反向结果说明单次波动不小，四个有区分力的任务里换一次运行，2/1/1 的分布可能变。这次的数字只够说明“两种行为都存在”，不够给出比例。
2. 约束是我从摘要里删掉的，不是摘要自然漏的。被删的句子周围还留着相关事实。
3. 任务是“写出决定”，模型没有真的动手。
4. 七条约束是我挑的，判定也是我一个人读的。
5. 这套配置下的新会话带 Team 的系统提示和工具定义。T6 的结果直接依赖这段系统提示里的那条指令。
6. A 和 B 的外壳都提到了 `history/`，C 没有。C 和 B 之间除了有没有原文，还差这两句话。
