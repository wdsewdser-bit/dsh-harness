## 做法：续跑上一次团队实测留下的现场，而不是重跑一遍

上一次实测的副本 `output/constraint-ledger-team-20261012/cod1` 停在这个故障上：`verifier` 被连续拒绝 17 次，`integration-lead` 被连续拒绝 10 次，两人的压缩后基线都还没交付。这正是要修的状态，直接在它上面续跑比重新花 45 分钟、上千个请求等它再出现更快，也更对题。

- 原地续跑（会话里记录的工作区路径是绝对路径，换目录会让成员写回旧目录）。上一次实测的结果文件已经提交，不受影响。续跑前把副本里将被替换的四个插件另存到 `cod1/plugins-before-item3/`。
- 插件：副本里的 `constraint-ledger.mjs`、`request-message-projection.mjs`、`team-v14-context-delivery.mjs`、`team-v12-runtime.mjs` 换成 staging 当前版本（前两个与生产现在的字节相同）。其余插件保持上一次实测时的生产版本。
- 配置不改：`contextPackMaxTokens` 仍是 32000。不为了触发而调小任何阈值。只把请求记录改写到 `requests-item3.jsonl`，不往旧的 562 MB 文件里追加。
- 权限、守护与上次相同：workspace-write / approval ask，生产会话、控制面、配置、真实工作区任何变化即停。
- 上限：60 分钟，500 个请求，先到先停。宿主 `driver/team-host.mjs --start --name cod1 --run item3`。

## 判定规则（先写下，看到结果后不改）

- **生效**：两名成员都至少进入一次回合；C1 对他们为 0；C2 至少有一人收到紧凑形态；收到的人随后至少完成一次工具调用。
- **未生效**：两名成员任何一人再次因为同一批可压缩来源（需求、裁定）被 `team-context-safety-debt` 拒绝。
- **另一种失败**：被拒绝的原因换成了不可压缩的来源（身份、名下任务）装不下。这说明紧凑形态不够，需要另行处理，如实报告。
- **没测到**：上限之内这两名成员没有被唤醒。此时改为在他们各自的会话里直接发消息再试一次，仍不行则报告没测到。
- C2 里若没有人收到紧凑形态而 C1 仍为 0，说明这次是完整形态就装下了（状态与上次不同），结论是“故障没有重现”，不算生效。

## 这次测试不能说明的

它验证的是“已经卡住的成员能恢复”。压缩刚发生时的第一条请求走的是同一段代码，但若续跑期间没有新的压缩（C6），这条路径就只被间接验证。紧凑形态下成员靠摘要工作的质量（会不会漏看验收条目）只看 C4 这一项，不做系统评估。
