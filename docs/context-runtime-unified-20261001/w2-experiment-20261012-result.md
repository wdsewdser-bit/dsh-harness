# W2 对照实验结果

日期：2026-10-12。作者：Claude。做法和判分事先登记在 [w2-experiment-20261012-protocol.md](w2-experiment-20261012-protocol.md)，执行中有一次偏离，记在该文件末尾。

## 结论

**按事先写死的规则，结果落在第一条：摘要压缩没有丢掉我挑的那几条早期约束，W2 维持名单模式，不再投入。**

但有两件事实比这条判定更值得看：

1. **这个根在生产里其实已经顶在主动压缩线上。** 任何一个新回合结束都会触发原生压缩，把 215.9 万字节的对话换成一份 1.3 万字节的摘要。W2 折叠把它降到 34%，所以折叠之后的那一回合没有触发压缩；但对话再长回 50%，压缩照样会来。W2 现在只是把压缩推迟，而不是替代它。
2. **压缩保住了叙述和结论，丢掉了绝大多数标识符。** 队友和成员在回报里写过的证据编号，压缩后只剩 4%；W2 是 100%。这些标识符后面用不用得上，这次实验没有回答。

第四组（小交接 + 按编号读原文）在同一天补跑了，见下面“第四组”一节：十道题全部答对，每个请求约 5.5 万到 8.9 万 token。登记的第三条规则也成立：**普通会话走第四组的形状，W2 只留给 Team 根。**

## 实际发生了什么

| 步骤 | 请求 | input | 其中缓存命中 | 交给适配器 | 说明 |
|---|---|---:|---:|---:|---|
| 不折，问 C1 | 1 | 536,311 | 76,160 | 2,253,215 B | 答对 |
| 运行时自动压缩 | 1 | 536,900 | 536,192 | 2,256,274 B | 输出 3,869 token 的摘要；“Compacted 388 history items” |
| 压缩后，问 A1 | 1 | 57,762 | 1,664 | 48,365 B | 答对 |
| 压缩恢复，模型自行调用工具 | 2 完成，2 被中断 | 59,279 和 76,723 | 57,728 和 59,264 | 52,274 B 和 113,058 B | 7 次只读调用后被我停掉 |

input 一列是适配器回报的 inputTokens 与 cacheReadTokens 之和。作为对照，W2 折叠后的后继请求是 336,759（其中命中 1,408），交给适配器 1,226,612 B。

三种状态下模型能看到的对话正文：

| | 消息数 | 字节 |
|---|---:|---:|
| 不折 | 384 | 2,158,609 |
| W2 折叠后 | 157 | 925,852 |
| 原生压缩后 | 3 | 28,778 |

压缩后的请求比 W2 折叠后的请求小一个数量级。单论之后每个请求的成本，压缩远低于 W2，这和决策文档里的推断一致，现在有了同一个根上的实测。

## 第四组：摘要 + 按编号读原文

授权：用户 06:25 UTC 回复“预算问题不用担心”。做法按登记方案，偏离记在登记文件“偏离二”。

- 新会话，工作区是沙箱目录，里面只有 `history/000.md` 到 `383.md`（384 条原始消息，每条一个文件）和 `INDEX.md`。访问模式 Read Only，审批关闭。

第一个请求的估算构成：工具定义约 4.5 万 token，系统提示约 0.4 万，摘要约 0.3 万。也就是说这个形状下每个请求的底价主要是工具定义，不是对话。

所有 11 次工具调用都是对 `history` 的 `grep`，没有读真实工作区，没有写入。停宿主后核对：747 个受保护的生产文件无变化，真实工作区和沙箱目录无文件变化。

### 第四组说明了什么，没说明什么

- **在“我知道要找什么”的前提下，摘要加可搜索的原文能把细节全部取回，包括压缩和 W2 都丢掉的那些。** 代价是每道题多一个请求（搜一次，答一次），每个请求和压缩后一样小。
- **它没有检验更难的那种情况：模型不知道自己忘了什么。** 十道题的题面都带着能直接拿去搜的关键词。真实工作里，被摘要漏掉的约束不会有人来提问，模型得自己意识到该去查。这次的数据对这一点没有任何说明。
- **搜索结果会留在上下文里。** 十道题之后正文涨了九倍。长时间这样用，仍然需要压缩，只是从一个小得多的起点开始。
- 这个会话并不是完全“普通”的：这套配置下新会话默认带 Team 的系统提示和工具定义，只是没有队友。这使每个请求的底价偏高，不影响答题对错。
- 第四组的摘要来自第二组，A4 和 C2 借用了同一会话里前面的内容，这两点登记时就列为局限。

## 怎么读这个结果

- **W2 的保真度是真的，但这次没有证据说明它保住的东西是后续工作需要的。** 被压缩丢掉的证据编号、等待票编号，控制面里都有记录，队友也可以重新报。十道题里，压缩丢的只是“+134 行”这种细节。
- **代价差一个数量级。** 压缩后每个请求约 5.8 万 token，W2 后约 33.7 万。
- **W2 现在挡不住压缩。** 主动压缩线是 50%，W2 折到 34% 之后对话继续增长，还是会被压缩。如果要让 W2 的保真度有意义，就得让它在压缩线之前自动触发，并且压缩要认得已经折过的窗口。这是一笔新的投入，而这次的数据不支持花这笔钱。

- **第四组给了普通会话一个更便宜的形状。** 摘要负责让每个请求变小，原文文件负责兜底。它比 W2 小一个数量级，细节取回率在这十道题上是 10/10，而 W2 折叠后的上下文里 B 类只有 1 道完整。但它依赖模型主动去查，这一点没有验证，所以我只把它当成“值得接着试的方向”，不当成已经成立的结论。

所以我的建议和登记的规则一致：W2 保持现状，不再加东西，也不必急着把今天修的步折叠部署到生产。今天的修复让它折得干净了（57% 对 37%），这在它被用到的时候是实打实的改进，可以随下一次常规部署带上。

## 没有做到的

1. 第四组只检验了“带着关键词去找”，没有检验“模型自己意识到该去找”。后者才是摘要压缩真正的风险所在，需要一个让模型继续干活、再看它是否违反被漏掉的约束的实验，这次没有做。
2. 前三组没有让模型逐题作答，只核对了答案是否还在上下文里。所以“模型在答案缺失时会不会编造”没有数据。
3. 一个根，一次压缩，一次折叠。压缩摘要的质量每次会不一样。
4. 压缩后的会话里，运行时的“压缩恢复”消息会让模型主动去查任务状态。这次它压过了我题目里的“禁止调用工具”。隔离副本的工作区路径是真实目录，这是隔离做法本身的缺口：今后在隔离副本上放开提问之前，要先把工作区也换成副本或者把权限设成只读。
